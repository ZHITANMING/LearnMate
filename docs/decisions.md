# 决策记录（Decision Log）

> 这个文件记录**每一个影响架构的决定**：做了什么决定、为什么、影响哪些模块。
>
> **规则**：架构允许演进，但必须是显式决定并写在这里，不能顺手改。
> 如果某个决定后来被推翻，**不要删掉原条目**——在后面追加一条「推翻」记录，并写明为什么改主意。
> 保留「当时的理由」比保留「正确的结论」更有价值，因为它防止同样的问题被重新争论一遍。

**记录格式**

```
## D<n> · <一句话决定>
日期：YYYY-MM-DD
状态：生效 / 已被 D<n> 取代
决定：
原因：
影响：
```

## D1 · 语言选 TypeScript / Node.js（strict 模式）

日期：2026-09-28
状态：生效

**决定：** 用 TypeScript（`strict: true`）在 Node.js 20 LTS 及以上运行。

**原因：** 本项目的数据契约（NoteDraft 的字段名、类型、约束）是产品核心。TypeScript 让契约在编译期就能被检查，字段名写错会直接报错，而不是等到运行时才发现知识库里混进了格式不对的笔记。Python 也能做，但类型约束是可选的，对非专业软件工程背景的开发者来说，TS 帮你挡下的错误更多。

**影响：** 引入 `typescript`、`tsx`/`tsc` 构建步骤；所有源文件为 `.ts`。

## D2 · 不自建 Markdown 阅读器，用现成编辑器查看

日期：2026-09-28
状态：生效

**决定：** 不开发 Web 界面或 GUI。生成的笔记用 Obsidian 或 VS Code 打开查看。

**原因：** 做一个「能看 Markdown」的界面大概是整个项目里最容易的部分，但它会吃掉一半时间，而且做出来一定不如 Obsidian 好用。把时间花在「整理质量」和「知识库不腐烂」这两件真正难的事上。

**影响：** 知识库目录必须对 Obsidian 友好（`.learnmate/` 用点目录，Obsidian 默认忽略）；v0.1 只做 CLI。

## D3 · 预览 → 用户确认 → 才写库

日期：2026-09-28
状态：生效

**决定：** `add` 命令在调用模型后，先把渲染结果打印给用户看，用户确认后才写入 `notes/`。

**原因：** 用户最不能接受的失败是「AI 把我写的东西弄丢了或者编造了」。预览确认是唯一能在**写入之前**拦住这类问题的机制。一旦坏笔记进了知识库，用户就得自己发现、自己清理——而大多数人不会去清理。

**影响：** `pipeline` 需要一条交互分支；引入退出码 0 的「用户取消」语义；提供 `--yes` 跳过确认（此时 `status = inbox`）。

## D4 · 扁平 `notes/` 目录 + frontmatter 标签分类

日期：2026-09-28
状态：生效

**决定：** 所有笔记平铺在 `notes/` 下，不建子目录。分类完全靠 frontmatter 的 `tags`。

**原因：** 目录树分类（`notes/机器学习/…`）要求用户在**写入时**就决定归属，而人在输入时往往还不知道这条笔记属于哪。更糟的是，一条笔记通常属于多个分类，目录树表达不了。标签可以后加、可以多个、可以改。

**影响：** 文件名 `<slug>-<id8>.md` 承担唯一性；`tags` 字段成为一级公民；未来的检索/图谱都从标签出发。

## D5 · LLM 只产出 JSON，Markdown 由确定性渲染器生成

日期：2026-09-28
状态：生效

**决定：** 模型被要求返回结构化 JSON（`NoteDraft`），经校验后由纯函数 `render` 生成 Markdown。**绝不让模型直接写 Markdown 当权威产物。**

**原因：** 让模型直接输出 Markdown 有四个致命问题：① 无法校验，格式错了也不知道；② 同一输入跑两次，格式会漂移，知识库风格不统一；③ 想改模板（比如加一个章节）就得重新调模型，成本高且不可靠；④ 无法做字段级 diff，`reprocess` 也就无从谈起。

**影响：** `contracts` 模块成为核心；`render` 必须是**确定性纯函数**；`reprocess` 可以零成本重渲染。

## D6 · 先冻结数据契约（`docs/03-contracts.md`），再写代码

日期：2026-09-28
状态：生效

**决定：** 在写任何业务代码之前，先把字段、目录、命名规则、写入顺序、退出码写成文档并冻结。

**原因：** 「AI 整理」最危险的地方在于它是一个黑盒——如果不对产出形状做硬性约定，模型每次会发明新字段，50 条笔记之后知识库退化成噪音。**schema 就是产品**，这件事必须先定。

**影响：** 所有模块以 `docs/03-contracts.md` 为准；改契约必须走第 11 节的变更流程。

## D7 · 台账用追加式 JSONL，不引入数据库

日期：2026-09-28
状态：生效
（本条**修正**了早期「用 SQLite 做索引」的建议）

**决定：** 运行台账用 `.learnmate/ledger.jsonl`（每行一个 JSON 对象，只追加）。v0.1 不引入任何数据库或 ORM。

**原因：** 重新权衡后发现，台账只需要两件事：**哈希查重**和**运行审计**。而查重所需的哈希本来就写在每条笔记的 frontmatter 里——也就是说，`notes/` 目录本身就已经是一份完整、可读、可 `grep` 的索引，再建一份数据库索引是重复的真相来源，还会带来「索引和实际文件不一致」这类新问题。

**升级触发条件**（满足任意一条就重新评估）：笔记数 > 5000，或 `list` 命令耗时 > 1s，或需要跨字段的复杂查询。

**影响：** `ledger` 是 IO 模块；台账是**派生数据**，删除后必须能由 `rebuild-index` 从 `notes/` 完整重建。

## D8 · `vault/` 放在仓库内，但被 `.gitignore` 忽略

日期：2026-09-28
状态：生效

**决定：** 知识库默认放在仓库内的 `vault/` 目录（相对路径的基准见 D12），但永不提交到 Git。

**原因：** 对新手而言，路径最简单（默认配置就能跑，不用理解绝对路径）。同时 `.gitignore` 保证私人笔记和密钥不会被 `git add .` 误提交——这是最可能发生、后果最难收回的事故。

**代价：** 笔记没有 Git 版本历史。（已记入技术债，见下）

**影响：** `.gitignore` 是 Task 1/2 的最优先产出；把知识库移出仓库是 v0.2 的话题。

## D9 · 正文用「受控块列表」取代固定段落骨架

日期：2026-09-28
状态：生效
（本条**推翻**了 R1 契约第 3.3 节的固定四段骨架）

**决定：** 笔记正文不再是「核心要点 / 关键概念 / 详细说明 / 待验证的问题」四个固定段落，而是一个 **`blocks` 数组**，由 6 种封闭枚举的块类型拼成：`text` / `steps` / `list` / `params` / `concept` / `uncertain`。

**原因：** 原设计假定输入是「说明文」，但用户真实的课程笔记是**操作手册**——主体是「做什么 → 点哪里 → 参数填什么 → 注意什么」，塞满菜单路径、参数名、快捷键。这种东西硬塞进「详细说明」就是一个垃圾场，正是阶段 1 警告过的「知识库退化成噪音」，而我自己踩了。
关键区分是：**固定的是积木的种类，不是积木的摆法。** 模型只能用这 6 种块、不能发明新类型，所以每条笔记可以长得不一样，但结构永远可校验、可检索。这样「用户的笔记没有固定形式」和「schema 就是产品」就不再矛盾。

**影响：** `contracts` 的块类型枚举成为核心；`render` 按块类型分派；`NoteDraft` 的字段从 8 个固定字段变成 `title/summary/language/tags/blocks`。

## D10 · 一次输入可以产出多条笔记（AI 负责拆分）

日期：2026-09-28
状态：生效

**决定：** `add` 的输入是**一整个文本**（例如一节课的笔记），AI 把它拆成 **1–15 条笔记**，每条独立成文件、独立成 id。输出结构从 `NoteDraft` 变成 `AnalyzeResult { notes: NoteDraft[] }`。用户逐条确认。

**原因：** 第一次输入的那 46 行里至少装了 10 个独立主题（软件设置 / 环境设置 / 素材导入 / 建立工程 / 两种做法做同一类效果 / 三款插件做同类效果 / 插件存预设…）。如果整份存成一条笔记，它本质上就是个文件夹——以后搜某个具体术语什么都搜不到，因为标题里没这两个字。
拆分粒度定为 **「一件你以后会单独想起来查的事」**：通用操作与具体效果必须分开，因为前者每节课都用，后者只在做这个效果时用。
批次的归属**靠 `source_hash` / `source_ref` 筛选，不写进 `tags`**——`tags` 只装知识维度的词，装批次信息会让标签体系很快变脏。

**代价：** 预览要确认 N 次（提供 `a` 一键全接受）；AI 可能拆错（提供 `n` 逐条跳过）。

**影响：** `raw/` 与 `draft/` 改用 `input_id` 命名（一次输入一个，原文只存一份）；台账一条笔记一行；`reprocess` 新增按来源重处理的入口。

## D11 · 存疑内容由用户在预览时逐条裁定

日期：2026-09-28
状态：生效
（本条**取代**了 R1 契约第 4.2 节的「拿不准的放进 questions」）

**决定：** AI 拿不准的内容不再只是「塞进 questions 段落」了事，而是写进 `uncertain` 块，在写入之前**逐条向用户提问**，用户选择 `k` 保留为「待确认」/ `d` 删除 / `e` 我来改写。`--yes` 时全部默认保留。

**原因：** 用户明确要求「拿不稳的做好是放入后询问用户如何处理」。原设计只是把不确定内容丢进一个段落，用户很可能根本不看，等于没处理。
同时补了一条更硬的内容准则：**技术细节逐字保留**——菜单路径、参数名、按键、插件名必须与原文完全一致，不许翻译或"顺手纠正"。因为 `按住 Ctrl 微调` 被改写成 `按住 Alt` 是一个**看起来完全正常、但会让你做错操作**的错误，比明显的胡说更有害。

**影响：** `pipeline` 的预览阶段多一层交互；`contracts` 新增 `uncertain` 块；台账新增 `uncertain_total` / `uncertain_kept` 字段。

## D12 · 配置里的相对路径以「当前工作目录」为基准

日期：2026-09-28
状态：生效（**修正**了契约第 8 节原先「相对仓库根目录」的措辞）

**决定：** `vaultPath` 这类相对路径，统一相对于**运行命令时所在的目录**（`process.cwd()`）解析，而不是相对于 `package.json` 所在目录。

**原因：** 「仓库根目录」需要向上逐级查找 `package.json` 才能确定，多一层会出错的机制；而 cwd 是现成的、且符合所有人对命令行的直觉——在哪个目录敲命令，文件就落在哪个目录。在常规用法（在仓库根目录跑 `learnmate`）下两者完全等价，但 cwd 的规则**可预测**，不会因为找不到 `package.json` 而变成第三种行为。
原本担心「在别的目录跑会写到奇怪的地方」，但配置文件本身也是按 cwd 找的，找不到就是「没有配置文件」，行为一致，不矛盾。

**影响：** `config.ts` 用 `resolve(baseDir, …)`，`baseDir` 默认 `process.cwd()`；契约第 8 节措辞同步改为「相对当前工作目录」。

## D13 · 配置文件里的未知字段直接报错

日期：2026-09-28
状态：生效

**决定：** `learnmate.config.json` 里出现不认识字段（如 `modle` 而不是 `model`）时，直接判为配置错误、退出码 2，并在能猜到时附一句「你是不是想写 model？」。

**原因：** 这是**拼错一个字母就静默失效**的一类问题：`modle` 被忽略后，用户会以为自己设好了模型，然后对着「model 必填」的报错完全摸不着头脑。宁可吵一点，也不要静默丢掉用户亲手写的配置。
提示用最短编辑距离 ≤ 2 的近似匹配来给，宁可不说也不乱猜。

**影响：** `config.ts` 维护 `KNOWN_KEYS` 白名单；新增配置项时**必须同时更新这个白名单**，否则用户写了新键反而报错。这是本决定的主要维护成本。

## D14 · 新增 `doctor` 子命令（原计划外）

日期：2026-09-28
状态：生效

**决定：** 在 T3（配置与密钥）里顺带做了 `learnmate doctor`：只读地打印当前配置、API Key 是否就位、提示词文件是否存在、Node 版本，并给出退出码。

**原因：** T3 的产物（`loadConfig`）在没有命令消费它之前是**无法验证的死代码**——用户没法亲手确认「我的配置读对了没有」。加一条只读命令，就把「读配置」变成了一个可以当场跑、当场看到结果的 MVP 验收点。原计划要到 T10 才有第一条真正用得上配置的命令。
`doctor` 严格只读：不调用模型、不创建目录、不写任何文件，所以它不会成为「验收入口」之外的新风险面。

**代价：** 多一个文件、多一条命令要维护；`main.ts` 里多一条子命令注册。

**影响：** 新增 `src/commands/doctor.ts`；`src/main.ts` 新增子命令注册与「异常 → 退出码」的统一处理函数（`handleFatal`）；帮助信息里多一条命令。

## D15 · 澄清契约第 5.5 节的「空行」与「字符数」

日期：2026-09-28
状态：生效（**澄清**契约第 5.5 节第 5、7 条的措辞，语义方向未变）

**决定：** 原措辞有两处会在实现时产生歧义，T4 落地时明确为：

- **第 5 条**「连续 3 个及以上空行折叠为 2 个」→ 指连续 **3 个及以上换行**折叠为 2 个换行，也就是正文里**最多保留一个空行**。
- **第 7 条**「超过 `maxInputChars`」→ 字符数按 **Unicode 码点**计（一个汉字、一个 emoji 都算 1 个，不是 UTF-16 长度），且**末尾那个由规范化补上的换行不计入**。

**原因：**

第 5 条按字面读（3 个空行折成 2 个空行）需要连续 5 个换行才触发，而结果是留下两个空行——这既几乎不触发，又不符合 Markdown 的排版习惯。显然本意是「清掉多余的空行」。
第 7 条若按 UTF-16 长度计，一个 `🎨` 会被算成 2 个字符，中文笔记的字数会虚高；若把末尾换行也算进去，用户把上限设成 20000、贴了正好 20000 个字，却被告知超了 1 个——这种差一个的错误最容易被当成 bug 上报，也最难解释。

**代价：** 契约第 5.5 节的措辞与最初冻结的版本不完全一致。已同步修改正文并在此留痕。**未改动任何字段名、目录位置、命名规则、块类型或写入顺序**，笔记数据格式不受影响。

**影响：** `src/core/ingest.ts` 的 `normalizeText` 与 `countInputCharacters`；`tests/ingest.test.ts` 覆盖这两条规则。

## D16 · 截断之后再去一次首尾 `-`

日期：2026-09-28
状态：生效（**澄清**契约第 5.3 节第 5 步，语义方向未变）

**决定：** 契约第 5.3 节的第 5 步（去掉首尾 `-`）在**第 7 步截断之后要再执行一次**。

**原因：** 九步是顺序执行的。标题很长时，截断到 60 个码点可能刚好落在原本位于中间的
`-` 上，于是产物的结尾又变成了 `-`，文件名里出现 `--`。第 5 步的意图显然是「产物不带首尾
`-`」，所以补执行一次是在澄清意图，而不是新增规则。

**代价：** 无。这条只影响长度超过 60 个码点、且第 60 个字符恰好是 `-` 的标题。

**影响：** `src/util/slug.ts` 的 `slugify`；`tests/vault.test.ts` 覆盖。

## D18 · frontmatter 的字符串值按需加双引号

日期：2026-09-28
状态：生效（**补充**契约第 3.3 节）

**决定：** frontmatter 里的字符串值，在满足以下任一条件时用双引号包起来：以 `- ? : , [ ] { }
# & * ! | > ' " % @ \`` 开头、含 `: ` 或 ` #`、以 `:` 结尾、形如数字或
`true`/`false`/`null`/`yes`/`no`/`on`/`off`/`~`、或首尾带空白。

**原因：** frontmatter 是 YAML。一个标题写成 `新建: 尺寸 1920` 时，`title: 新建: 尺寸 1920`
在 YAML 里是语法错误——整段 frontmatter 会解析失败，而**失败得非常安静**：文件还在，
Obsidian 只是不再认得 `tags`、`status` 这些字段，笔记从此在视图里「失踪」。
用双引号而不是单引号，是因为只有双引号支持反斜杠转义，标题里带引号时才有救。

**代价：** 渲染产物与契约示例（第 3.4 节）在个别标题上会多出引号。这是对的行为——
示例里的标题恰好不含 `: `，所以两者仍然逐字符一致。

**影响：** `src/core/render.ts` 的 `yamlScalar` / `needsQuotes`；`tests/render.test.ts` 覆盖
（`render：YAML 安全`）。

## D20 · `input_id` 写进每一条笔记的 frontmatter

日期：2026-09-28
状态：生效（**修订**契约第 3.1 节，字段从 13 个变 14 个）

**决定：** frontmatter 增加 `input_id`，值与产生这条笔记的那次输入相同。它在字段顺序里紧跟在 `id` 后面。

**原因：** `raw/<input_id>.txt` 和 `draft/<input_id>.json` 都是按 `input_id` 命名的。在加这个字段之前，笔记文件里**没有任何东西**指向自己的原文和草稿——那个线索只存在台账里。而台账按契约第 9 节是**派生数据**，`rebuild-index` 会拿 `notes/` 把它整个重写一遍。于是出现一个自相矛盾的处境：

T7 写 `rebuild-index` 时撞上了这个矛盾。当时的选项有两个：① 重建时合成一个假 `input_id`，接受 `reprocess` 在台账丢失后退化；② 加一个字段，让 `notes/` 自成闭环。

## D22 · `rebuild-index` 的语义：`ok` 由笔记派生，其余原样保留

日期：2026-09-28
状态：生效（**补充**契约第 9 节，新增 9.1 / 9.2 两个小节）

**决定：** `rebuild-index` 是**唯一**会重写 `ledger.jsonl` 的代码路径（`add` 只追加）。重建时：

| 条目 | 笔记文件 | 处理 |
|---|---|---|
| `outcome = ok` | 在 | 沿用原条目（保住 tokens / 耗时 / 存疑统计），只刷新 `title` / `tags` / `status` / `note_path` / `source_hash` |
| `outcome = ok` | 不在 | 剔除 |
| 非 `ok` | —— | 原样保留 |

**原因（三条各自独立）：**

- **为什么允许重写**：契约说台账「只追加，禁止重写历史」。但同时也说它是派生数据、删了要能重建。这两句话在有损坏行时是冲突的——重建必然要重写整个文件。明确划定「`rebuild-index` 是唯一例外」，比留一句自相矛盾的话好。
- **为什么 `ok` 且笔记还在就沿用旧条目**：新造的条目里 tokens 和耗时只能是 0。明明台账里有真实数字，却因为「重建」把它冲成 0，是纯粹的倒退。**重写文件不等于放弃里面的信息。**
- **为什么 `ok` 但笔记没了要剔除**：台账的第一用途是查重。一条指向已删笔记的 `ok` 记录会让用户**再也录不进这份内容**，而且没有任何提示说明为什么。反过来，删除一条笔记时用户的意图本来就是「不要它了」。
- **为什么非 `ok` 要原样保留**：失败、取消、跳过**按定义没有笔记文件**，如果重建只信 `notes/`，这些记录会在第一次重建时全部消失。它们除了台账没别处记得，而「我那次输入到底怎么了」正是台账存在的第二个理由。

**代价 / 已知缺口：** 重建不回来的字段（`tokens_in` / `tokens_out` / `latency_ms` / `uncertain_total` / `uncertain_kept`）一律补 0。补 0 是「不知道」而不是「是零」，这一点写进了契约 9.2。另外，重建会**抹掉台账里读不懂的行**（断电留下的半行），所以 `rebuild-index` 必须把这个行数报出来——不报，用户就永远不知道曾经有过。

**影响：** `src/io/ledger.ts` 的 `rebuildLedger`（返回 `RebuildReport`，含 `reused` / `created` / `dropped` / `keptHistory` / `damagedLines` / `unreadable`）、`src/commands/rebuild-index.ts`、`tests/ledger.test.ts`。

## D23 · 提示词文件是系统消息，用户原文是用户消息

日期：2026-09-28
状态：生效（**补充**契约第 4 节，新增 4.7）

**决定：** `prompts/<promptVersion>.md` 的内容**只是规则**，作为系统消息发送。用户的笔记原文作为**用户消息**发送，**不进提示词文件**。文件里唯一的占位符是 `{{TAG_VOCABULARY}}`（已有标签词表），组装时纯字符串替换；出现别的 `{{...}}` 或不配对的花括号一律报错。

**原因：**

- **为什么原文不进文件**：原文最长 20000 字符（`maxInputChars`）。如果把它拼进提示词，提示词文件就不再是「能从头读到尾的一份规则」，而是一份规则加一段可能几百行的素材——用户要迭代提示词时，得先穿过自己的笔记才能看到自己要改的那句。而且同一个 `promptVersion` 会对应到内容完全不同的文件，`promptVersion` 写进 frontmatter 的对照价值就没了（「这条笔记是哪个提示词产出的」变得无法比较）。
- **为什么占位符只有标签词表**：它是**唯一**会随运行而变、且属于「规则」而非「素材」的东西（契约 4.6 第 5 条要求复用已有标签）。所以它留在提示词里。其余变量都属于素材。
- **为什么不用模板引擎**：一个 `{{NAME}}` 替换用 `split().join()` 就够了，模板引擎会多一个依赖，还会带来「表达式、条件、循环」这些一旦有了就会被用上的东西——而提示词里出现条件逻辑，意味着同一份提示词在不同输入下走不同分支，`promptVersion` 就不再能描述「模型看到的是什么」。
- **为什么未知占位符要报错而不是原样保留**：如果原样发给模型，`{{TAG_VOCABULARY}}` 写成 `{{TAG_VOCABULARY }}` 或 `{{TAGS}}` 的结果是「模型收到一个自己看不懂的记号」，而模型**不会报错**——它会猜，或者干脆忽略，然后输出一个看起来正常、但标签没复用词表的结果。这类错误必须在我方炸掉，才有人知道。
- **为什么必须有占位符、且恰好一次**：没有它，提示词就没法注入标签词表，契约 4.6 第 5 条落不了地；出现两次，说明文件被误编辑过，替换哪一处都有 50% 的概率是错的。

**代价 / 已知缺口：** 提示词文件本身无法被自动化测试（它的正确性只能靠「拿真实笔记跑一遍，看拆出来的东西对不对」）。因此 T8 的验收方式是**读**，真正的验收落在 T9/T10。另外 `{{TAG_VOCABULARY}}` 在文件里位于「已有标签词表」小节，程序不做位置校验——替换只要发生一次即可。

**影响：** `prompts/analyze.v1.md`、契约 §4.7、T9 的 `src/core/analyze.ts`。

## D24 · 允许 `notes` 为 0 条，但把它限定成「最后手段」

日期：2026-09-28
状态：生效（**修改**契约 4.1：`1–15 条` → `0–15 条`；补充契约 6.2 的产出 0 条行为）

**决定：** `AnalyzeResult.notes` 允许为空数组。原文里确实没有任何可复用的知识内容时（例如只有一句「今天没学什么」），模型返回 `{"notes": []}`；pipeline 打印一段说明、**不写 `notes/`、不写台账**、退出码 **0**。

**原因：**

- **为什么必须开这个口子**：不开的话，模型面对没有内容的原文时**唯一的出口就是编**。契约 4.6 第 1 条（不新增原文没有的事实）是本项目最重要的内容规则，而 1–15 条的下界恰好和它冲突——两个规则打架时，模型会挑那个更容易被满足的（凑一条出来）。**与其让它编，不如给它一条明确的退路。**
- **为什么退出码是 0**：什么都没出错。原文读到了、模型跑通了、结果也合法——只是结论是「没东西可整理」。用 3（校验失败）会让用户以为出了问题，然后去查一个不存在的 bug。
- **为什么必须说出来**：0 条和「跳过」一样是**静默无输出**。如果不打印，用户看到的就是「命令跑完了，知识库里什么都没有」——这和崩溃在观感上完全一样。这个项目已经有一条类似教训（`rebuild-index` 最初会静默抹掉损坏行）。
- **为什么台账不记**：台账每行的必填字段里有 `id`，而 0 条时根本不存在笔记 id。为它硬造一个 id 会污染「台账的每一行都指向一条笔记」这个不变量。代价是同一份内容再贴一次会重新分析一次——可以接受，因为产出 0 条的原文本来就不值得缓存。

**代价 / 已知缺口：** 模型可能偷懒（原文其实有内容却返回 0 条）。防线有三道：① 提示词第一节第 7 条 + 第二节点名「难懂不是返回空 的理由」+ 自检清单里专门一问；② 终端明确打印「这次没有可整理的笔记」，用户当场能发现；③ `raw/` 与 `draft/` 照样落盘，原文不可能因为 0 条而丢失。**这三道防线能不能真的挡住偷懒，要等 T9 拿真实笔记跑过才知道。**

**影响：** 契约 §4.1 / §6.2、`prompts/analyze.v1.md`、`tests/prompt.test.ts`、T9 的校验器（必须把 `{"notes": []}` 判为合法）。

## D25 · 模型服务地址进配置项 `baseUrl`，默认 DeepSeek

日期：2026-09-28
状态：生效（补充契约 §8 配置契约）

**决定：** 新增配置键 `baseUrl`，默认 `https://api.deepseek.com/v1`。程序在它后面拼 `/chat/completions`，用 OpenAI 兼容的请求/响应格式。`model` 仍无默认值、必填。

**原因：**

- **为什么不把地址写死在代码里**：写死等于把「换一个模型服务」变成「改代码 + 重新发版」。这个项目大概率要换（便宜的、更聪明的、或者公司内网的），而换的时候用户不该碰源码。

## D26 · 只有「输出不合契约」才重试；网络与 HTTP 错误一律不重试

日期：2026-09-28
状态：生效

**决定：** `analyze` 的重试预算（`maxRetries`，默认 2，即最多调用模型 3 次）**只花在一种失败上**：模型回了内容，但内容过不了 `validateAnalyzeResult`。`io/llm.ts` 抛出的 `LlmError`（超时、连不上、401/429/4xx/5xx、对方返回的不是 JSON）会直接穿过 `analyze` 抛给用户，**一次都不重试**。

**原因：**

- **重试对这两类失败的作用完全相反**。输出不合契约时，把「你哪里错了」回喂给模型，第二次真的更可能对——这是有信息量的重试。而网络错误、401、429 是**与内容无关**的失败：立刻重发同一个请求，只会再撞一次同一堵墙（429 尤其如此，重试是加重而不是缓解）。
- **401 重试会变成「悄悄试三次密钥」**。用户看到的是「跑了很久然后失败了」，而不是「你的 Key 不对」。错误被拖延本身就是一种误导。
- **钱**。重试是在同一个问题上重复付费。花在「模型答错了」上值，花在「网线断了」上纯粹是浪费。

**已知缺口：** 429 与 5xx 其实可以通过退避重试救回来，但 v0.1 不做——用户手动再跑一次的成本更低，而且他能看到真实的失败原因。将来要加的话，必须只对 429/5xx 加，并且要有明确的次数与退避上限。

**影响：** `src/core/analyze.ts`、`src/io/llm.ts`、`src/core/errors.ts`（`ValidationError` 退出码 3 / `LlmError` 退出码 4）、契约 §7。

## D27 · `--dry-run` 连原文都不写

日期：2026-09-29
状态：生效（**补充**契约 §6.1：`--dry-run` 是「原文先落盘」的唯一例外）

**决定：** `learnmate add --dry-run` 全程零写入——**连第 1 步的 `raw/` 都不写**。它照常读输入、照常调用模型、照常走预览，只是把每一次写入换成一行打印。

**原因：**

- 契约 §6.1 说第 1 步「唯一不可跳过、不可撤销」。这句话存在的理由是「先保住用户的输入，再去调模型」——防的是模型失败或断电让用户白打一遍字。而 `--dry-run` 的字面承诺是「一个文件都不写」。如果它还偷偷写一份 raw，这个开关就变成了「大部分不写」：用户为了试一份敏感内容（病历、公司内部文档、别人的东西）跑 `--dry-run`，结果这份内容静静地留在了磁盘上。

- 代价是 `--dry-run` 之后没有 raw 可供 `reprocess`。可以接受：试跑的目的就是决定「要不要真的跑一次」，真跑了 raw 自然会有。

**代价 / 已知缺口：** `--dry-run` 仍然会**真的调用模型**（会花钱）。这一点必须打印出来（命令层已打印「（--dry-run）会照常调用模型，但一个文件都不会写。」），否则用户会以为试跑是免费的。

## D28 · `q` 是「取消整批」，不是「停止继续问」

日期：2026-09-29
状态：生效（**补充**契约 §6.2）

**决定：** 预览时按 `q` 退出 → **这一批一条笔记都不写**，包括在此之前已经答过 `y` 的那些。退出码 **0**。

**原因：**

- 预览是写入前唯一的拦截机制，所以「写到一半」这个状态必须不存在——它是最难向用户解释的状态（「到底写了几条？」「台账里有几条？」「剩下的草稿还能不能恢复？」）。要么整批算数，要么整批不算。
- 退出码仍是 0：用户主动不做，不是程序出错（契约 §7 的规则）。
- `q` 之后原文与全部草稿都保留，所以「取消」不损失任何东西——重新跑一次就有完整的预览。

**代价 / 已知缺口：** 用户确认了 9 条、第 10 条按 `q`，前 9 条的确认白做。将来可以加「只写入已确认的」分支（`q` 之前已有 `y` 时多问一句），v0.1 不做——多一个分支就多一个半完成状态的入口。

## D29 · TD8 的守卫：写入前算全部目标文件名，撞名则整批不写

日期：2026-09-29
状态：生效（**实现**契约 §5.3 与 decisions.md 的 TD8）

**决定：** `pipeline` 在写任何一条笔记之前，先把这一批**全部**目标文件名算出来，检查两件事：① 批内是否有两条会写到同一个文件；② 磁盘上是否已经有同名文件。任一命中 → 抛新的 `UnsafeWriteError`（退出码 **3**），**这一批一条都不写**，原文与全部草稿照常保留。比较文件名时**忽略大小写**。

**原因：**

- **为什么必须整批不写**：半写成功的批次状态很难解释（用户得自己数 `notes/` 里哪些是这次的），而原文和草稿本来就安全——整批退回去的代价只是「把这两段内容拆成两次输入再跑一遍」，说明文字里已经写清楚了。
- **为什么也用退出码 3，而不是 2**：契约 §7 规定**退出码 1 与 2 不产生任何写入**，而走到这一步时 `raw/` 与 `draft/` 早就写下去了。用 2 会让「2 = 零写入」这条承诺变成谎话，而契约的可靠性正建立在「退出码能说明磁盘状态」上。
- **为什么单独一个错误类型**（不复用 `ValidationError`）：`ValidationError` 要保住的是「模型回了什么」（所以它带 `rawOutputs`，并写 `quarantine/`）；撞名时模型输出完全合法、也已完整躺在 `draft/` 里，现场不需要再抄一份。两件事的救援方式不同，混成一个类型只会让用户读到「模型输出不合契约」这种完全错误的解释。
- **为什么忽略大小写**：Windows 与 macOS 的默认文件系统不区分大小写，「Config」和「config」在那里是同一个文件。第一版守卫用原样比较，测试里正是这一条把问题暴露出来的（断言写的是小写文件名，实际输出是大写）。

**代价 / 已知缺口：** 只做了大小写折叠，**没有做 Unicode 归一化**（NFC/NFD）与全角半角折叠，见 TD10。

**影响：** 契约 §5.3 / §7、`src/core/errors.ts`（`UnsafeWriteError`）、`src/pipeline.ts`（`assertSafeTargets`）、`tests/pipeline.test.ts`。

## D34 · 提示词升到 `analyze.v2`，收紧拆分粒度

日期：2026-09-29
状态：生效

**决定：** 新建 `prompts/analyze.v2.md`，把 `DEFAULTS.promptVersion` 与 `learnmate.config.example.json` 升到 `analyze.v2`。**`prompts/analyze.v1.md` 保留不删，但示例文本已按脱敏要求替换为中性词（见 D38 补充）。**

**原因：** 前两次真实运行（第一份输入 1379 字拆出 13 条、第二份输入 1752 字拆出 15 条）暴露出四个提示词层面的缺陷。它们都不是代码 bug——代码忠实地执行了 v1，是 v1 第五节「拆分准则」的措辞在鼓励碎拆：

1. **粒度失控。** 1379 字拆 13 条、1752 字拆 15 条（106 / 117 字符一条）。两份主题毫无关系的输入，比例却几乎一致——说明这是模型的稳定习惯，不是某份输入的性格。v1 的措辞是「按**可独立复用的知识点**拆」，而「知识点」在实践中被理解成了「一句话」。
2. **`summary` 与正文重复。** 有一条笔记 859 B，而正文实际只有 34 个汉字——`summary` 是正文的换句式重写；另一条的正文里有两行逐字相同。v1 只规定了 `summary` 的长度，**从没说过它是干什么用的**。
3. **流程被按步骤拆开。** 第二份输入那 15 条的标题连起来是一条有先后的操作流程，而「顺序」只活在其中一条 34 字的笔记里。**流程的价值就在顺序，拆成多个文件就丢了**——将来照着做还得在文件之间找路。
4. **同一主题被拆成「父 + 两个子」三条。** 一条笔记写「同一类效果有两种做法」，另两条分别写两种做法各自怎么操作。同主题被拆了三次，而且父子三条谁都不是超集。

v2 针对这四点逐条加了约束：粒度下限与「遮住 `summary` 还剩什么」测试、`summary` 是索引不是正文的预告片、一个完整流程装进一条笔记（**超过 15 步就在同一条里拆成两个 `steps` 块**——`LIMITS.stepsItemsMax` 是 15，这不是把笔记拆成两条的理由）、同主题的多种做法必须合并（并点名了「父 + 两个子」这种三重拆分）。另加了一条条数自查线——初版写的是「原文 2000 字以内不该超过 8 条」，但对照实验证明这条线不管用（1752 字的输入稳定产出 9～10 条），已改为**按密度算**：原文 ÷ 条数，**平均每条不该少于 150 字**（1379 字最多 9 条、1752 字最多 11 条）。这个判据经得起检验：v2 的三次产出（8 / 9 / 10 条）全部通过，v1 的两次（13 / 15 条）全部不通过。

**为什么不改 v1 而是新建 v2：** 已经落盘的 28 条笔记，frontmatter 里写着 `prompt_version: analyze.v1`。那个字段是指向一个**具体文件内容**的永久引用——改掉 v1 的正文，这 28 条笔记就再也解释不清自己是怎么来的（D23 的理由）。而且 v1 的产出留在库里就是现成的对照组，同一份原文可以在两个版本下直接比。由此补一条契约（§4.7）：**发布过的提示词文件永不删除、永不改写**。

**代价 / 已知缺口：**

- 提示词变长，`tokens_in` 会上升。这是为「更少的碎片笔记」付的钱。
- **`TEMPERATURE = 0` 也不保证可复现。** 两次实证：v1 时代同一份原文，`--dry-run` 拆出 14 条、正式拆出 13 条；**v2 自己也有**——同一份原文、同一个 `analyze.v2.md`，第一次 `--dry-run` 拆出 9 条，第二次拆出 10 条。差别只在「导入素材与素材尺寸处理」被拆成了两条（`素材在目标软件中的导入与整理` + `素材尺寸过大与各部分素材的处理`），其余 8 条逐字吻合。所以 v2 的效果**只能靠对照实验统计，不能靠单次运行下结论**：大的合并是稳定的，边界上的判断会翻。
- TD7（拆分粒度不可控）**只是缓解，没有解决**：用户仍然不能主动要求「拆粗一点」，也不能把两条笔记合并。

**对照实验的实际结果（2026-09-29 补记）：** 同一份原文在 v1 与 v2 下各跑一遍：第一份输入 **13 条 → 8 条**，第二份输入 **15 条 → 9～10 条**，合计 28 条 → 17～18 条。v1 那三处「父 + 两个子」三重拆分（两种做法做同一类效果、三款插件做同类效果、两个步骤串成一条流程）在 v2 里**全部合上了**；第二份输入的 9 条里有 8 条标题带括号说明合并了什么。那条 859 字节 / 34 汉字的退化笔记没有再出现。粒度问题基本解决。

**`summary` 这一条先坏后修，修法是「摘要退让」。** 第一次对照实验抓到：某条笔记的 `summary` 是「把素材复制进新建文档后先导出一张整体图，再**用快捷键**打散、分散到图层，各部分分别导出。」，而正文第一个 `steps` 块把它拆成了 3 条编号步骤——其中第 3 条与 `summary` **连续 23 个字符逐字相同**，正是 §2.1 第 1 条要禁的。模型把 `summary` 当成了提纲，**换了形状（一句话 → 编号列表）却没换内容**。据此给 §2.1 加了第 3 条：明确禁止「把 `summary` 拆成编号列表再写一遍」，写明正确做法是「正文从 `summary` 停下的地方接着写」，并附上这个真实反例。

**加了第 3 条之后重跑，这条修好了**（同一份原文，`--dry-run --force`）：`summary` 变成「把素材复制进新建文档后先导出一张整体图，再打散分层，各部分分别导出。」；正文第一个 `steps` 块把原来的第 3 条拆成了「打散，分散到图层。」与「各部分分别导出。」两条；**最长逐字重合从 23 字降到 7 字**（「先导出一张整体」「各部分分别导出」）。另外那两条快捷操作也从编号步骤里挪出来、独立成了 `## 打散后的处理`——顺带修掉了一处真实的分类错误（「打散」和「成组」本来就不该塞在同一个步骤里）。

**但要看清它是怎么修好的：模型没有「从 `summary` 停下的地方接着写」，而是把摘要的长句切碎，让每一段的公共子串都短于 10 字。** 摘要和正文仍然在讲同一件事，只是不再逐字重合。代价是**摘要退让了一档**——丢了那个快捷键，只说「再打散分层」。这个代价可以接受：摘要负责「这条讲什么」，正文负责「具体怎么做」，快捷键本来就该归正文。

**这条规则的教训：用字符数上限来定义「不许重复」是可以被绕过的**，字面达标不等于意图达标。真正绕不过去的判准应该是「**摘要里每个短语是否都能在正文里找到对应步骤**」——如果答案是「能」，那就是摘要抄了正文，跟字符数无关。这次没有继续收紧，因为重复的绝对代价已经很小（就一行引用块），而且这条笔记的另外两块（`打散后的处理`、`分别导出的两种方法`）本来就不在摘要里，它已经不是空壳了。将来如果要在 v3 里重做这一条，应该直接换成那个绕不过去的判准。

注意 `src/core/render.ts:327` 会把 `summary` 以 `>` 引用块的形式渲染进正文，所以摘要本来就一定出现在笔记里——这条规则约束的是**六个块**，不是那个引用块。

**影响：** `prompts/analyze.v2.md`（新建）、`src/config.ts`（`DEFAULTS.promptVersion`）、`learnmate.config.example.json`、`tests/prompt-file.test.ts`（守卫改为按版本参数化，v1 与 v2 都要过一遍）、`docs/03-contracts.md` §4.7、`README.md`。

## D35 · 台账记下每一次输入的结局（两种行 / 两个新 outcome）

日期：2026-09-29
状态：生效

**决定：** 把契约 §9 的台账条目从「一种扁平结构」改成**按 `outcome` 判别的两种行**：

- **笔记行**（`outcome: 'ok'`）：字段与 T10 之前**逐字相同**，一次输入产出 N 条笔记写 N 行。
- **输入行**（`outcome ≠ 'ok'`）：**一行 = 一次输入**，字段只有 `ts`、`input_id`、`source_hash`、`model`、`prompt_version`、`outcome`、`reason`、`draft_total`、`skipped_total?`。

同时新增两个 `outcome` 值 `empty`（模型说没有可整理的）与 `unsafe_write`（目标文件名撞名，整批不写），并立下契约 §9.3 的核心不变量：**只要 `raw/<input_id>.txt` 存在，台账里就必须有至少一行带这个 `input_id`。**

**原因：** TD11 记的是「这四种情况下没有 `note_path`，写行会让台账指向不存在的文件」。在 T11 里翻知识库时抓到了它的**实际后果**：`vault/.learnmate/raw/01M3NQS4SPPTFZY58V0F2DTSZY.txt`（1 个字节，就一个换行）与同 id 的 `draft/01M3NQS4SPPTFZY58V0F2DTSZY.json`（`{"notes": []}`）都在，**台账里一行都没有**。也就是说：一次真实发生过的输入在记忆里完全不存在了，而且**没有任何办法事后发现它**——`rebuild-index` 从 `notes/` 重建，失败的输入不在 `notes/` 里，所以重建出来的台账照样是「干净」的。这不是少了一条日志，是台账会撒谎。

于是有了那个不变量。它的好处是三条同时成立：它是测试能断言的、`doctor` 能体检的、用户拿 `ls` 和 `type ledger.jsonl` 就能眼睛验证的。

**为什么是判别联合而不是给输入行填空值。** 备选方案是保留扁平结构，把 `note_path` / `title` / `tags` / `note_index` 等填成 `''`、`0`、`[]`。改动确实更小（不用动 `isLedgerEntry` 与 `compareEntries`），但它会造出一堆**没有任何东西强制其含义**的假字段：一个空的 `note_path` 看起来像「路径是空字符串」，而不像「这一行没有路径这回事」。将来写 `list` 或统计的人会对这些零值做判断，然后判断错。判别联合让「这一行没有这些字段」变成**类型层面的事实**，代价是读取端两处要跟着改（见下）。

**为什么 `empty` 要单独立一个值，不和 `skipped` 合并。** 两者的**主语不同**：`empty` 是「模型判断原文里没有可复用的知识点」，`skipped` 是「用户决定不要这一条」。合并成一个 `skipped` 之后，按 `outcome` 一筛就再也分不出「模型什么都没看出来」和「用户看不上」——而这恰恰是 T12 做查询时最想区分的两件事。而且这次抓到的孤儿现场（`draft` 里是 `{"notes": []}`）正是出口 5 留下的，它就是那个「曾经无法被看见」的结局。

**为什么 `duplicate` 保留定义却不写。** 命中查重时 `add` 是**成功且什么都没发生**（退出码 0，原文根本没落盘）。按不变量，它不属于必须记录的输入；而按「台账是记忆不是日志」的定位，它也不该每次重跑都往里塞一行「已存在」。但契约 §9 已经发布过这个值，历史文件里可能有它，所以**读取端必须继续认得它**——实现上用一个更窄的类型把「可以写出来的 outcome」和「读取端必须接受的 outcome」分开。

**为什么写台账失败不许改变原来的退出码。** 写下这一行的时机恰恰是「已经出事了」的时候（校验失败、网络失败、撞名）。如果这时磁盘满或权限不对，让台账的异常盖掉原来的错误，用户看到的就是一个假的失败原因（甚至可能变成退出码 1「未预期异常」），而真正该修的问题被埋掉了。所以追加那一行是**尽力而为**：失败只打一句警告，原来的错误照原样抛。

**代价 / 已知缺口：**

- 读取端有两个地方必须跟着改，而且都得改对：`isLedgerEntry` 的放宽**只能按 `outcome` 分支校验该分支用途真正依赖的字段**（`ok` 行要 `id`，两种行都要 `input_id` / `source_hash` / `outcome`）。多校验一个字段不会更安全，只会让升级前写下的行集体变成「损坏行」——而损坏行会在下一次 `rebuild-index` 里被静默抹掉。
- 排序：输入行没有 `note_index`，`compareEntries` 把它当 `0`，于是它排在这一批笔记之前。这是有意的（先看结局，再看产出），但它意味着**同一 `input_id` 的行不再全部相邻且按序号排**。契约 §9.1 的「跑两次逐字节相同」仍然成立，但成立的理由从「字段齐全」变成了「缺失值有确定的替代值」。
- 契约 §9 里 A1 那一版把 `skipped_total` 写成了「只有 `skipped` 才有」，而 §2 的出口 6 又要求 `cancelled` 也给出条数。**两处不一致，这里按后者实现**：`skipped_total` 在 `skipped` 与 `cancelled` 上都有，含义是同一个（用户按 `n` 跳过了几条；`cancelled` 记的是按 `q` 之前已经答过 `n` 的条数）。把数字放进字段而不是写进 `reason` 的句子里，是因为 `reason` 明确是「给用户看的、程序不解析的」。
- 模板坏掉（`analyze` 组装系统消息时抛 `UsageError`，退出码 2）**仍然不写台账行**，而这时 `raw/` 已经落盘了——这是不变量的一个已知例外，留在 TD14。
- 仍然不记 `note_total` 之外任何跨输入的东西；不做统计、不做报表（T12）。

**影响：** `docs/03-contracts.md` §9（§9.1 排序、§9.3 新增）、`src/core/contracts.ts`（`LedgerOutcome` 增两值、`LedgerNoteRow` / `LedgerInputRow` / `LedgerEntry` 判别联合、`LedgerInputOutcome` / `LedgerRecordableOutcome`）、`src/io/ledger.ts`（`OUTCOMES`、`isLedgerEntry`、`findSuccessfulBatch`、`collectKnownTags`、`rebuildLedger`、`compareEntries`）、`src/pipeline.ts`（`buildInputEntry` / `recordOutcome` 与 5 个出口）、`tests/ledger.test.ts`、`tests/pipeline.test.ts`。

## D36 · 标签词表从笔记本身收集，不再问台账

日期：2026-09-29
状态：生效

**决定：** 填 `{{TAG_VOCABULARY}}` 的取词函数 `collectKnownTags` 从 `src/io/ledger.ts` 搬到新的 `src/io/notes.ts`，数据来源从「台账里 `outcome: 'ok'` 的行」改成「`notes/` 里每条笔记 frontmatter 的 `tags`」。行为上只有两点不同：**去重后的顺序是首次出现顺序**（排序仍然交给 `renderTagVocabulary`，保证提示词逐字符稳定），以及**读不懂的笔记跳过**（一篇坏文件不该让整次输入失去词表；坏在哪由 `doctor` 报告）。原函数直接删掉，不留 `@deprecated` 转发——留着它就会有人继续用，而它返回的东西从此是错的。

**原因：** 这条链是这样的——`add` 把词表拼进系统消息（契约 §4.7），提示词要求「优先复用已有标签」（契约 §4.6）。也就是说「用户用过哪些标签」这件事决定了模型会不会自己另起一个同义词。而 T12 之前这个词表的**唯一**来源是台账，可台账是**派生数据**：契约 §9 与 `docs/05-recovery.md` 都明确写着「整份删掉 `ledger.jsonl`，再跑 `rebuild-index` 就能重建」。两条都是文档**允许用户做**的操作，做完之后台账里 `outcome: 'ok'` 的行会被重建（标签还在，这部分没问题）——但 `rebuild-index` 重建不回历史行（§9.2），而更早的一次性风险是：万一用户只删不重建，或台账损坏到 `readLedger` 跳过大量行，**「优先复用已有标签」这条设计就会静默失效**，模型开始造同义词，用户看不出任何异常。这正是 TD3（标签同义词爆炸）最不想要的加速方式。

更根本的理由是那句已经写在 `docs/02-architecture.md` 第 133 行的话：**台账是索引，笔记文件是真相。** 只要 `notes/` 在，标签就一定在，因为标签本来就写在每条笔记的 frontmatter 里（D20 让笔记自成闭环，D4 让标签可以后加、多个、随时改）。既然信息在真相里，取词就不该绕道派生数据。

**为什么 `tags` 命令与 `add` 必须共用同一个函数。** T12 新增的 `tags` 命令会把词表原样打给用户看。如果它自己遍历一遍 `notes/`、而 `add` 继续问台账，用户就会看到两份可能不一致的清单，而且**没有任何东西会告诉他们不一致**。所以两者都必须调用 `src/io/notes.ts` 的同一个 `collectKnownTags`，`tags` 命令的输出格式（一行一个标签）只是 `renderTagVocabulary` 给出的同一个顺序的另一种呈现。测试里有一条专门钉住这件事。

**代价 / 已知缺口：**

- `collectKnownTags` 从「读一行行 JSON」变成「读一遍目录里所有笔记并解析 frontmatter」，代价随笔记数线性增长（每次 `add` 多一次全量读）。当前 28 篇无感；这与 D7 的升级触发条件（笔记数 > 5000 或 `list` 耗时 > 1 秒）是同一笔账，到那时再说。
- 词表不再包含「只出现在台账、但笔记文件里已经没有」的标签。这类标签只在手工删过笔记、或台账被手工改过的情况下出现，而那时候台账才是不该被信的那个。
- `list` 与 `tags` 从此都不再读台账（D37），所以**失败的输入历史在浏览命令里看不到**。这是有意的：要看得用将来的 `history` 命令，而不是把浏览命令绑在可删的八种形状的派生物上。

**影响：** `src/io/notes.ts`（新增）、`src/io/ledger.ts`（删除 `collectKnownTags`）、`src/pipeline.ts`（改 import 与注释）、`docs/03-contracts.md` §4.7、`tests/notes.test.ts`（新增）、`tests/pipeline.test.ts`（用例翻转）。

## D37 · 浏览命令只读笔记文件；`id8` 不再是句柄；`show` 拿不准就报候选

日期：2026-09-29
状态：生效

**决定：** T12 新增的三个只读命令 `list` / `show` / `tags` 一律**从 `notes/` 读，不读台账**；`list` 显示完整 26 位 ULID 而**不显示 `id8`**；`show` 匹配到多于一篇时**绝不猜**，打印候选清单并以退出码 2 结束。三条一起写进契约 §11。

**原因（为什么浏览命令不读台账）。** 契约 §9 与 `docs/05-recovery.md` 都明确允许用户「整份删掉 `ledger.jsonl`，再跑 `rebuild-index`」。如果 `list` 读台账，用户做完一次**文档允许的操作**之后，`list` 就会说「知识库还是空的」，而 `notes/` 里几十篇一篇没少——**命令输出了与事实相反的话**，这是最坏的一类 bug：用户没有任何办法判断该信哪个。此外台账有**两种行**（笔记行 / 输入行，字段不同，见 §9.3），从里面拼出「有哪些笔记、什么标题、什么状态」本来就要跨两种行归并；而 `outcome: 'ok'` 行记的 `title` / `tags` / `status` 也可能比笔记文件旧（笔记是真相，台账是索引——`docs/02-architecture.md` 第 133 行）。

代价：**失败的输入历史在浏览命令里看不到**。这是有意的取舍，留给将来的 `history` 命令——而不是把浏览命令绑在一个可删的派生物上。

**原因（为什么 `list` 不显示 `id8`）。** 文件名是 `<slug>-<id8>.md`，而 `list` 本来就显示标题；文件名比标题多出来的信息只有那个 `id8`。而 `id8` 在真实数据里**已经撞了**：一库几十篇笔记里，13 篇共用同一个 `id8`、15 篇共用另一个（同一毫秒内写入的同批笔记共享 ULID 前缀）。显示它等于递给用户一个**会误伤**的把手：`show 01m3nr4j` 只会得到「13 篇候选」。所以 `list` 直接不给这个把手，`show` 的候选里给**完整 id**。想按名字查的路没堵死——`show` 的匹配规则本来就把文件名（去掉 `.md`）也当子串匹配，所以 `show 示例笔记-先做-A-再做-B-01m3nrxy` 照样能唯一定位。要让 `id8` 重新变唯一，得改文件名格式，那是另一块工作（§11.5 明确写了）。

**原因（为什么 `show` 多篇时退出码 2 而不是取第一个或最近一个）。** 猜错一次的代价不是「多打一行字」，而是**用户以为自己看的是 A、实际是 B**，并且他无法察觉——三条笔记的正文都像模像样。宁可让用户把关键词写长一点再跑一次。「0 篇」与「多篇」都返回 2（用法/无法确定），因为两种情况下用户要做的动作是同一件事：去看 `list` 或把关键词写具体。

**补充（`show` 的正文从哪里切）。** `show` 默认要打的是「frontmatter 之后的正文」，而 `parseFrontmatter` 只回答「这篇读不读得懂」，不回答「正文从第几个字节开始」。于是 `src/core/frontmatter.ts` 增加了**第二个导出** `noteBody(markdown): string | null`——这是对 D21「只导出 `parseFrontmatter`」的一次**扩展**，不是推翻：D21 拒绝的是「引一个通用 YAML 库」，而 `noteBody` 用的仍是同一条 `---` 分隔线规则、同一个「只认自己写出去的子集」的立场。它与 `parseFrontmatter` 的失败语义**故意不同**：解析失败意味着「读不懂」，而取正文失败**不代表没有正文可看**——那种文件照样整篇打出去，所以 `noteBody` 返回 `null` 而不抛错，由调用方决定怎么办。正文是**原样切片**（按 `\n` 切开后丢掉分隔线之前的行），不做任何重新排版，只去掉分隔用的那行空行。

**代价 / 已知缺口：**

- 用户查不到「上次那次输入为什么没成功」——`validation_failed` / `llm_error` / `empty` 只存在于台账里。留给 `history`。
- `id8` 一旦出现在别的地方（日志、笔记文件名、用户自己的笔记），它就仍然是个会撞的字符串；本次只保证 **LearnMate 自己的输出不引导用户去用它**。
- `list` 每次要解析全部笔记的 frontmatter，代价随笔记数线性增长（与 D36 同一笔账，触发条件见 D7：> 5000 篇或 `list` > 1 秒）。

**影响：** `src/commands/list.ts`（新增）、`src/commands/show.ts`（新增）、`src/commands/tags.ts`（新增）、`src/io/notes.ts`（新增 `readNoteSummaries`）、`src/core/contracts.ts`（新增 `NoteSummary`）、`src/main.ts`（注册三个命令）、`docs/03-contracts.md` §11、`tests/list.test.ts` / `tests/show.test.ts` / `tests/tags.test.ts`（新增）。

## D38 · `reprocess` 的对象与两条路径：默认零模型调用，`--reanalyze` 才花钱

日期：2026-09-29
状态：生效

**决定：** 新增 `reprocess` 命令，把「已经存在的一份分析结果」重新变成笔记文件。对象用**显式选项名**指定，三选一：`--input <input_id>`（重渲染这一次输入的全部笔记）、`--note <26 位笔记 id>`（只重渲染这一篇）、`--source <source_hash>`（按指纹反查 `input_id`）。**默认路径一个字节都不问模型**：从 `draft/<input_id>.json` 读回草稿、按 `resolutions/<input_id>.json` 重放用户当年的裁定，再 `renderNote` 一遍。只有 `--input <input_id> --reanalyze` 才重新调用模型（第 4 节）。一个都不给时**打印能重处理的候选清单并以退出码 2 结束**；一个 `--source` 命中多个 `input_id` 时同样打印候选并以 2 结束。语法与全套规则写进契约 §12。

**原因（为什么不用位置参数）。** `input_id` 与笔记 `id` 都是 26 位大写 ULID，形状完全一样，`reprocess 01M3NR4A…` 分不清用户想说的是「这一次输入」还是「这一篇笔记」，而两者要写的文件完全不同。显式选项名把这个歧义在**语法层**消掉，而不是靠猜或者靠再问一遍。

**原因（为什么一个指纹对多个输入时退 2 而不是照做）。** 实测真实数据里 `sha256:5c095fff…` 对应**三个** `input_id`（其中两个各有十几条笔记、一个是被 `q` 取消的那次）。挑一个来重渲染，用户以为自己在修 A、实际改的是 B，而且他没有任何办法察觉——与 D37 给 `show` 定的立场是同一条：**拿不准就问，不替用户猜**。无参数时报 2 而不是 0，是为了不让「我什么都没指定」看起来像「我成功重处理了全部」。

**原因（为什么默认路径不读原文、不需要 API Key、断网也能跑）。** 重渲染的输入只有两样：草稿与裁定。`raw/<input_id>.txt` 只有一种情况下才需要——元数据全缺、要靠它重算 `source_hash`。默认路径不读它，也就不需要模型、不需要密钥，这是「省钱」这个卖点最实在的形态：T13 之前，每一次「想换个排版」都得再付一次模型调用。

**元数据从哪来（这是默认路径最麻烦的部分）。** `draft/<input_id>.json` 的内容**就是** `AnalyzeResult`（`{notes:[…]}`），里面**没有** `id` / `created` / `updated` / `status` / `source_hash` / `model` / `prompt_version` / `source_ref`——元数据必须找回来。优先级写进契约 §12.3 的表：`source_hash` 先问台账、再问既有笔记的 frontmatter、最后才从 `raw/` 重算（`src/util/hash.ts` 的规范化是幂等的，所以重算得到的指纹与原笔记一致）；`model` / `prompt_version` 只在前两个来源里有，两处都没有就**退出码 3**，并明确告诉用户「这次输入没有留下生成记录，只能用 `--reanalyze` 重新分析」——绝不编一个默认值填上去。

**原因（靠标题匹配，不靠 `note_index`）。** 草稿第 k 条对应盘上哪一篇笔记，只能靠**标题**对上。用台账里的 `note_index` 是不行的：用户按 `n` 跳过时台账只记 `skipped_total` 这个计数、没记跳过的是哪几条，而 `rebuild-index` 重建的 `note_index` 是按 id 排序重新推的，跳过的空档会被抹平。依据是 `src/core/validate.ts` 的 `validateAnalyzeResult` 强制**同一批内标题不重复**（重复就整批校验失败）。台账的 `note_index` 只当**一致性校验**用：能对上就信，对不上就以标题为准并打一行警告。对不上草稿的盘上笔记**不动它**，只在末尾列出「这 N 篇笔记在这次草稿里找不到对应，已跳过」；反过来草稿里有、盘上没有的，就按新笔记写出来（新造 id）。

**原因（内容没变就一个字节都不写）。** 新渲染出来的 Markdown 与盘上那一篇**逐字节比较**，完全一样就什么都不写——连 `updated` 也不动。这样 `reprocess` 是**真幂等**的：连跑两次，第二次零写入。`updated` 的用法因此是「只有内容真的变了才刷新」而不是「每次重处理都刷新」，用 `dir vault\notes` 看修改时间就能一眼判断「有没有被改」。这也让「逐条写、中途崩了」的恢复方式成立：重跑一遍，已经写好的那几篇会被认成「未变化」（写进 `docs/05-recovery.md`）。

**代价 / 已知缺口：**

- 手改过 `draft/` 的标题、或 `slugify` 规则变了，算出来的文件名会与原来不同——这时是「新名字写出来、旧名字留在盘上」，不会自动删旧的那篇。要删得用户自己动手（`trash/` 只服务于 `--reanalyze` 换掉自己造出来的那批）。
- 默认路径**不做整体事务**：写到第 3 篇时崩了，前 2 篇是新的、剩下的还是旧的。这不需要补救机制（重跑即可），但用户得知道「看到一半的现场是正常的」。
- 撞名守卫要从「目标已存在就整批拒绝」泛化成「允许白名单里的目标被覆盖」（`assertSafeTargets`）。白名单**只有本次要重写的这几篇自己的目标路径**；白名单之外的文件存在照样整批拒绝（D29 的精神不变）。这是 T13 唯一一处动了 `add` 已经在用的代码。
- 不做 `--all`：一次改 28 篇笔记，没有版本控制兜底（D8），风险不对等（契约 §12.7）。

**影响：** `src/core/reprocess.ts`（新增，纯函数）、`src/core/resolutions.ts`（新增，纯函数）、`src/commands/reprocess.ts`（新增）、`src/pipeline.ts`（新增 `runReprocess`、`assertSafeTargets` 泛化）、`src/main.ts`（注册 `reprocess`）、`src/io/vault.ts`（`resolutions/`、`moveNoteToTrash`）、`docs/03-contracts.md` §12、`tests/reprocess.test.ts`（新增）。

## D39 · 默认重渲染**不写台账**，一行都不写

日期：2026-09-29
状态：生效

**决定：** `reprocess` 的默认路径（重渲染）**不往 `ledger.jsonl` 里写任何一行**，命令结束时打印一句「台账没有改动；要看刷新后的索引请运行 `learnmate rebuild-index`」。`--reanalyze` 不受此限——它是一次**新的输入**，按契约 §9.3 的八出口表正常记账。

**原因（三条）。** ① 台账记的是**每次输入的结局**（`ok` / `skipped` / `cancelled` / `validation_failed` / …），而重渲染**不改变任何一次输入的结局**：那批笔记还是那次输入产出的，只是重新渲染了一遍。为它写一行 `ok`，等于把「用户又跑了一次 reprocess」伪装成「用户又录入了一次」。② 台账是**只追加**的（`appendText`，契约 §6.4 唯一的非原子写），而重渲染真正要动的是既有 `ok` 行里的**派生字段**（`title` / `tags` / `status` / `note_path`）——按契约 §9.1，刷新这些字段**正是 `rebuild-index` 的职责**（D22 已经把这个分工定死了）。硬要写就只能追加一堆与旧行冲突的新行，让台账里同一次输入出现两套真相。③ **零契约变更**：不需要新增 outcome 取值、不改两种行的形状、不动八出口表——T13 因此没有碰台账契约一个字。

**代价（以及为什么可以接受）。** 重渲染之后，台账里的 `ok` 行会与 `notes/` 暂时对不上（比如用户手改过标题，或渲染规则变了）。对策不是让 `reprocess` 顺手重建，而是**把话说清楚**：结束时提示跑 `rebuild-index`，并写进 `docs/05-recovery.md`。这与 D22「`add` 也不自动重建」的立场一致：两个命令各自做一件事，用户手里始终有一个明确的、可单独执行的动作。

**备选与代价：** 新增一个 `reprocessed` outcome。要改契约、要改 `LedgerInputRow` 的语义（它记的是「输入」，而重渲染不是一次输入）、行还会越积越多，而且它并不是一个「结局」。不采用。

**影响：** `src/pipeline.ts` 的 `runReprocess` 默认分支（不调 `appendEntries`）、`docs/03-contracts.md` §12.5、`docs/05-recovery.md`。

## D40 · 存疑项的裁定写进 `resolutions/<input_id>.json`，**不碰 `draft/`**

日期：2026-09-29
状态：生效

**决定：** 用户在预览里对存疑项做的 `d`（删除）/ `e`（改写）裁定，写到**新文件** `vault/.learnmate/resolutions/<input_id>.json`，形状是 `{ input_id, ts, notes: [{ note_index, items: [{ item_index, text, action, resolution? }] }] }`。`draft/` **一个字节都不改**。只记非 `keep` 的裁定（`keep` 是默认值）；一条非 `keep` 都没有时**不写这个文件**。写入时机是**预览循环结束之后、撞名守卫 `assertSafeTargets` 之前**的一次原子写（这样「笔记文件在 ⇒ 重放需要的裁定也在」）。`--dry-run` 不写；用户中途按 `q` 取消整批时不写。

**原因（为什么不回写 `draft/`）。** `draft/` 的定位是**「模型到底回了什么」的证据**（D31）。用户改了什么是另一个作者、另一件事，混进去会让这份证据同时有两个来源，事后没人能分清「模型说的」和「用户改的」。而且回写只能表达「删掉/改写」这两种结果里的**结果**，表达不了「用户当初是对哪一条做的这个决定」——一条被 `d` 掉的存疑项直接消失，将来想复盘「当时为什么删它」就没有任何线索了。分开存还有一个实际好处：`draft/` 的格式一个字节都不用动，`schema_version` 保持 1，28 篇已发布笔记与 4 个旧草稿一个都不用迁移。

**原因（为什么要新开一个目录，而不是放进 `draft/`）。** `src/io/vault.ts` 的 `listFilesIn(dir, extension)` 按扩展名过滤，把 `xxx.resolutions.json` 放进 `draft/` 会被 `listDraftFiles` 当成**一份草稿**——`doctor` 的孤儿体检、`rebuild-index` 的输入、将来的任何扫描都会多出一份读不懂的「草稿」。换文件名（比如 `xxx.res.json`）能绕过扩展名过滤，但那让两个目录里躺着两种语义不同的东西，下次谁加一个按 `*.json` 全收的扫描又会踩同一个坑。一个新目录把「这是另一类东西」写进结构里。

**原因（为什么带 `item_index` 与 `text` 两个坐标）。** `item_index` 用来定位（重放时按下标找那一条），`text` 用来**校验**（对不上说明这个文件被手工改过、或者草稿换了）。规则是**降级、绝不静默、也绝不硬套**：`item_index` 越界或 `text` 对不上 → 打一行明确警告，**这一条按 `keep` 处理，其余裁定照常应用，整次重渲染继续**；整个文件读不出合法 JSON → 同样打警告，按「没有任何裁定」重渲染。理由：一条坏记录不该让整次重处理失败，但更不能把它硬套到另一条存疑项上——那等于替用户说了一句他没说过的话。

**重放用不到这一层的任何新渲染逻辑。** `UncertainItem.resolution` 字段契约里本来就有，`src/core/render.ts` 早就把它渲染成 `  - 更正为：…`，`src/core/validate.ts` 的注释也写明「模型不该产出它，预览流程会覆盖」。T13 只是把预留的管道接上：`drop` = 重放时把该条从 uncertain 块里移除，`edit` = 给该条补上 `resolution`。**改渲染器不是 T13 的工作。**

**`--reanalyze` 之后旧裁定自然失效。** 新分析产生的是**新 `input_id`**，`resolutions/<旧 id>.json` 不会命中，不需要任何额外的作废逻辑。这也符合直觉：重新分析就是从零开始，不该把上一次的裁定悄悄带过去。

**影响：** `src/core/contracts.ts`（`UncertainRulingAction` / `UncertainRuling` / `NoteRulings` / `ResolutionFile` / `ResolutionParse` / `RulingApplication`）、`src/core/resolutions.ts`（新增）、`src/io/vault.ts`（`RESOLUTIONS_DIR` / `resolutionFilePath` / `readResolutions` / `writeResolutions` / `listResolutionFiles`）、`src/pipeline.ts`（`runAdd` 累积裁定并落盘）、`docs/03-contracts.md` §2 与 §12.4、`tests/resolutions.test.ts`（新增）、`tests/vault.test.ts`、`tests/pipeline.test.ts`。

## D41 · `--reanalyze` = 新造 `input_id` 再跑一遍 `add`，旧笔记**搬进回收站**而不是删除

日期：2026-09-29
状态：生效

**决定：** `reprocess --input <input_id> --reanalyze` 把 `raw/<input_id>.txt` 里那份**已经规范化过的原文**当成一次**全新的输入**，走与 `add` 完全相同的分析链路（读模板 → 收集词表 → `analyze` 含「只有校验不过才重试」→ 预览 → 存疑项 → 台账八出口）。它**新造一个 `input_id`**，把同一份原文再写一份 `raw/<新 id>.txt`、分析结果写 `draft/<新 id>.json`；**旧的 `raw/` / `draft/` / 台账行一律不动**（那是历史，`draft/` 是 write-once）。用户**确认之后**，把同一 `input_id` 的旧笔记**移进** `vault/.learnmate/trash/`（撞名规则 `trash/<原文件名>`，已存在则 `trash/<base>.<n>.md`，`n` 取最小可用正整数），然后才写新的那一套。

**为什么复用 `runAdd` 而不是另写一套。** 分析、校验、重试、预览、存疑项交互、台账八个出口——这些行为必须与 `add` **一模一样**；抄一份出来的那天，就是两者开始分叉的那天。`--reanalyze` 与 `add` 的差别只有三处：**跳过查重**（用户明确要求重来，不再调 `findSuccessfulBatch`）、**产出新 `input_id`**（`runAdd` 内部 `newId()` 造的）、**写新笔记之前把旧笔记搬走**。为了后两点，`runAdd` 增加了两个可选回调 `beforeWrite`（第一次真的要把字节写进 `notes/` 之前调一次，`--dry-run` 也会调）与 `afterCancel`（这一批一条都没写时调一次），`--reanalyze` 用它们搬走 / 搬回。

**为什么顺序必须是「分析 → 校验通过 → 用户确认 → 搬旧的 → 写新的」。** 这样用户按 `q` 取消、或全部答 `n` 时，旧笔记**原封不动**。反过来先搬再问，一次误触就会让库里少一批笔记——而 `vault/` 不在 Git 里（D8），没有版本可回退。

**为什么搬进 `trash/` 而不是原地删掉，也不是原地保留。** 删掉不可逆（D8 没有回退手段），而这一步换掉的正是「模型自己刚产出的一批」——出错了应该能捞回来，所以是**搬**不是删；`trash/` 在契约里本来就是回收站（`trashFilePath` 早已在用）。备选「旧笔记原地保留」不采用：库里会永久留着**两代重复笔记**，而 `rebuild-index` 会把两代按同一个 `source_hash` 归成**一组**，那组里的 `note_total` 会凭空翻倍、排序也会乱。搬走之后台账里的旧 `ok` 行会在下一次 `rebuild-index` 时被**剔除**（契约 §9.1：`ok` + 文件不在 → 剔除），这正是想要的效果，命令结束时照例提示跑 `rebuild-index`。

**已知缺口（崩溃窗口）。** 搬到一半、或搬完旧的还没写完新的时崩掉，`notes/` 会缺这一批，而它们在 `trash/` 里——可恢复（`docs/05-recovery.md`）。没有整体事务，与默认路径同一个立场。

**为什么 `--reanalyze` 产出的笔记没有 `source_ref`。** `raw/<input_id>.txt` **只存正文、不存源文件名**，源文件名只有原笔记的 frontmatter 记得，台账和草稿里都没有。这是 `--reanalyze` 与 `add --force` 的**唯一信息损失**，写进契约 §12.5。

**不新建 `prompts/analyze.v3.md`。** `--reanalyze` 用配置里的 `promptVersion`（默认 `analyze.v2`），新笔记 frontmatter 如实记这个值。已发布的提示词文件永不删改（D34）。

**影响：** `src/pipeline.ts`（`runReanalysis`、`runAdd` 的 `beforeWrite` / `afterCancel` / `ingestOverride`）、`src/commands/reprocess.ts`（`--reanalyze` 分支才 `requireApiKey` / 读模板 / 建聊天函数）、`src/main.ts`（注册 `--reanalyze`）、`src/io/vault.ts`（`moveNoteToTrash`）、`docs/03-contracts.md` §12.5、`tests/reprocess.test.ts`。

## D42 · v0.2 从 `.docx` 起步：抽取发生在任何写入之前，`raw/` 存的是抽出来的文本

日期：2026-10-07
状态：生效

**决定：** `add` 增加第三种输入——`.docx`。按扩展名（忽略大小写）识别，先把 `word/document.xml` 抽成纯文本，再走与文本输入**完全相同**的规范化（§5.5）、指纹（§5.4）与落盘路径（`raw/<input_id>.txt` 存的是**抽出来的文本**）。抽取失败一律退出码 2、零写入。**不新增任何依赖**：ZIP 的中央目录自己解析，解压用 Node 自带的 `node:zlib`。

**为什么是 `.docx`，而不是路线图里同列的 PDF 与图片 OCR。** 三者里只有 `.docx` 能做到**零新增依赖且不冒质量风险**：它就是一个 ZIP 包着一个 XML。反过来，无依赖抽 PDF 文本对中文几乎不可靠（中文 PDF 常靠字体子集 + 自定义编码，抽出来是乱码或空白），OCR 则要么装外部引擎（Tesseract），要么调用视觉模型——**这两条都会把「一个 CLI」变成「一个需要先装环境的系统」，或者把用户的笔记图片发给第三方**。所以 v0.2 先交 `.docx`；PDF 与 OCR 的取向留给用户决定（外部工具 / 加依赖 / 先不做），不替他选。

**为什么抽取必须在任何写入之前。** 契约 §7 承诺退出码 1 与 2 零写入，而 `raw/` 是**第一个**写入动作（硬约束 4）。若先落原文再抽取，一份损坏的 `.docx` 就会在库里留下一个字节的原文、却没有台账行——正是 TD14 那个「不变量例外」的翻版。把抽取放进 `readInput`（`add` 的第一步）之后，这条新路径天然不破坏承诺：抽取失败时 `raw/` 还没写。

**为什么 `raw/` 存抽出来的文本，而不是原始 `.docx`。** 存原始字节有三个问题：`raw/` 就不再是「规范化文本」而混着二进制（它现在是 `.txt`，`reprocess` 也把它当文本读）；把源文件复制进知识库等于给用户的私人文档多留一份副本（D8：`vault/` 不在 Git 里，没有版本可回退）；而 `raw/` 的用途是「让笔记解释得了自己是怎么来的」，不是「备份源文件」。代价是**抽取规则将来变了就没法重抽**——已写进契约 §5.6 与 TD16。

**为什么自己解 ZIP，而不是装一个库。** 读取器只做两件事：从中央目录里找出 `word/document.xml`、把它解压出来。为此拉一个压缩库进来不划算（本项目运行时依赖只有 commander）。天花板明明白白写在 `src/io/readers/docx.ts` 的文件头和契约 §5.6 里：不支持 ZIP64 / 加密包 / 分卷，不校验 CRC，只读不写（**永远不会去写 `.docx`**）。

**为什么只认 `<w:t>`。** 抠文字的难点不是「怎么删标签」，而是「**哪些字符才算正文**」。先翻译结构、再把标签全删掉的做法有一个隐蔽的坑：**元素之间的空白也是字符**，而真实的 `document.xml` 在 `<?xml …?>` 后面就带一个换行——那样一份完全正常的文档抽出来会平白多一个空行；更糟的是 `w:pPr` 这类以 `<w:p` 开头的标签，一旦靠字符串前缀分派，会再插一堆空行（这两条都是实测撞出来的，`tests/docx.test.ts` 里有用例守着）。现在规则只有一条：**除了 `<w:t>` 的内容和几个能翻译成空白的结构标记，什么都不留**。副作用是修订删除的文字（存在 `<w:delText>` 里）也不会出现在笔记里——那正是想要的。

**为什么按扩展名判断，而不是嗅探内容；为什么编码不猜。** 嗅探错了的后果是**静默产出乱码笔记**：乱码也是「文字」，用户当场看不出来，直到回头查笔记才发现。扩展名是用户明确给出的信息，就算判断错了也是可解释、可纠正的（改个名字再跑）。同理，文本一律按 UTF-8 读，**不猜 GBK**：猜错同样是静默的。这条有代价——GBK 保存的 `.txt` 会读成乱码并照常送进模型，不报错（已记 TD16）。

**顺带修掉一处文档与代码不一致。** 契约 §3.1 的 `source_ref` 示例原本写着「`示例输入.txt` 或 `stdin`」，但**没有任何代码写过 `stdin`**：从标准输入读时 `sourceRef` 是 `undefined`，`pipeline` 明确不写这个字段（`tests/frontmatter.test.ts` 与 `tests/render.test.ts` 都守着「没有就不出现」）。本次把**文档**改成与实际一致，而不是改代码去补一个 `stdin`——写一个假文件名比不写更糟：`list --source stdin` 会让人以为那是一次真实来源。

**影响：** `src/io/readers/docx.ts`（新增）、`src/commands/add.ts`（`readInput` 增加 `.docx` 分支，并改为导出以便测试）、`src/main.ts`（`[source]` 参数说明）、`docs/03-contracts.md` §3.1 + §5.6 + §7、`tests/docx.test.ts`（新增 34 例，覆盖段落/表格/实体/压缩方式/四种读不了的输入，以及「XML 自己的排版不进正文」这条回归）。

## D43 · v0.2 收口：只交 Word（`.docx`），PDF 与图片 OCR 推迟

日期：2026-10-07
状态：生效

**决定：** v0.2 的交付范围就是 v0.1 的文本输入加上 `.docx`（D42）。**PDF 与图片 OCR 这一版不做，也不给目标版本**——路线图里它们从「v0.2 会新增」改成「推迟，等真实需求」（`docs/01-project-brief.md`）。`package.json` 的版本随之从 `0.1.0` 升到 `0.2.0`。

**为什么不做，而不是「先做个能跑的版本」。** 这两条路都不是加几十行代码的量级，而且它们的失败方式正好落在本项目**最不能接受**的那种上（`docs/01-project-brief.md`：内容被弄丢或被编造，优先级高于「整理得漂亮」）：

- **PDF**：中文 PDF 普遍靠字体子集加自定义编码，不引入依赖自己抽，抽出来常常是乱码或空白；要抽得可靠就得加依赖（`pdfjs-dist`）或者要求用户先装外部工具（`pdftotext` / Poppler）。前者抽取质量仍然不保证，后者把「`npm install` 完就能跑」变成「先配好环境」——与本项目运行时只依赖 `commander` 的立场相反。
- **图片 OCR**：要么装 Tesseract 加中文语言包（同样把 CLI 变成需要配环境的系统），要么把笔记图片发给第三方视觉模型。后者与本项目自己的隐私立场冲突：`vault/` 与笔记内容是私人的（`AGENTS.md`：不要读取、打印或复制；D8：不把 `vault/` 放进 Git），为了让工具读图而把它们上传到外部服务，得由用户明确点头。

而且**乱码是静默的**——它同样是「文字」，用户当场看不出来（TD16 已经为编码记过一次同样的教训）。宁可在入口处明确失败，也不要产出一份看起来正常、回头才发现内容全错的笔记。

**为什么把「不做」也记成决策。** 路线图原来写着 v0.2 = 图片 OCR / PDF / Word；不改它，文档就在说谎。而且「推迟」与「忘了做」在半年后看起来一模一样——留下这条，是为了下次翻到时知道这是**一次带着理由的选择**，不是遗漏。

**什么条件下重新考虑。** 用户手头确实有 PDF 或扫描件，并且愿意为它装一个外部工具（或明确同意把图片送出去）。届时的顺序：先让「识别不了的输入明确报错」，再做抽取；抽取一律沿用 D42 的规矩——发生在**任何写入之前**，失败退出码 2、零写入。

**影响：** `package.json`（`0.2.0`）、`README.md`（版本横幅）、`docs/01-project-brief.md`（版本路线表）。**没有代码改动。**
