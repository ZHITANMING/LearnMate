## 1. 术语表

| 术语 | 含义 |
|---|---|
| **输入 / Input** | 用户一次性交给工具的一整段文本（可能是整节课的笔记） |
| **原文** | 输入的原始文本，未经任何加工 |
| **规范化文本** | 原文经 `ingest` 处理后的文本，用于哈希、分析、落盘 |
| **指纹** | 规范化文本的 SHA-256，表示为 `sha256:<64 hex>` |
| **笔记 / Note** | 知识库里的一条 Markdown 文件。**一次输入可以产出多条笔记。** |
| **草稿 / NoteDraft** | 单条笔记的结构化数据，LLM 被允许产出的唯一形状 |
| **块 / Block** | 笔记正文的组成单元，类型封闭枚举，见第 3.3 节 |
| **知识库 / vault** | 存放笔记与内部数据的目录 |
| **台账** | `.learnmate/ledger.jsonl`，追加式审计记录，属派生数据 |

## 2. 知识库目录布局

```
vault/
├─ notes/
│  └─ <slug>-<id8>.md            ← 笔记文件（唯一的人类可见产物）
└─ .learnmate/
   ├─ raw/<input_id>.txt         ← 规范化文本（原文，按「输入」存，不按「笔记」存）
   ├─ draft/<input_id>.json      ← 一次输入的全部草稿（NoteDraft 数组）
   ├─ resolutions/<input_id>.json← 用户对存疑项的 d/e 裁定（重放用，见第 12 节）
   ├─ ledger.jsonl               ← 台账
   ├─ quarantine/                ← 校验失败的现场
   └─ trash/                     ← 回收站：被换掉的笔记（`<原文件名>`，撞名加 `.<n>`）
```

规则：

1. `vault/` 位置由配置 `vaultPath` 决定，默认 `./vault`（相对**当前工作目录**，见 decisions.md D12）。
2. `vault/` **永不进入 Git**（已在 `.gitignore` 中）。
3. `notes/` 是**扁平**目录，不再建子目录；分类靠 frontmatter 的 `tags`。
4. `.learnmate/` 以点开头，Obsidian 默认忽略。
5. `raw/` 与 `draft/` 按 **`input_id`**（一次输入一个 ULID）命名，**不按笔记 id 命名**——因为一次输入可能对应十几条笔记，原文只存一份。
6. **只有 `src/io/vault.ts` 有权读写以上任何一个路径。**
7. `resolutions/` 与 `raw/`、`draft/` 一样按 **`input_id`** 命名。它**不放进 `draft/`**：`listFilesIn(dir, extension)` 按扩展名过滤，`xxx.resolutions.json` 会被 `listDraftFiles` 当成一份草稿。
8. `trash/` 里放的是**整个笔记文件**（不是片段），只用文件名命名；撞名时加 `.<n>` 后缀（`n` 取最小可用正整数）。`trash/` 就是契约意义上的回收站，`trashFilePath` 早已在用它。

## 3. 笔记文件契约

### 3.1 frontmatter 字段

| 字段 | 类型 | 必填 | 约束 | 示例 |
|---|---|---|---|---|
| `id` | string | 是 | ULID，26 字符，Crockford Base32 大写 | `01J8ZC4M7QX2V9K3TB6NPRW5HE` |
| `input_id` | string | 是 | ULID；**同一次输入拆出的所有笔记共享它** | `01J8ZC4M7QX2V9K3TB6NPRW5HE` |
| `title` | string | 是 | 1–80 字符，单行 | `示例笔记：先做 A 再做 B` |
| `created` | string | 是 | ISO 8601 带时区偏移 | `2026-09-28T21:31:26+08:00` |
| `updated` | string | 是 | 同上；重处理时更新 | `2026-09-28T21:31:26+08:00` |
| `summary` | string | 是 | 1–300 字符，单行 | `先做第一步，再做第二步，得到目标效果。` |
| `tags` | string[] | 是 | 1–5 个，每个 1–20 字符，不含 `#` 与换行 | `[示例标签, 演示, 占位]` |
| `status` | enum | 是 | `inbox` \| `processed` \| `reviewed` | `processed` |
| `source_hash` | string | 是 | `sha256:` + 64 位小写十六进制 | `sha256:3f2a…` |
| `source_ref` | string | 否 | 来源标识；**只存文件名，绝不存完整路径**。从标准输入读时这个字段整条不出现 | `示例输入.txt` |
| `schema_version` | integer | 是 | 当前为 `1` | `1` |
| `language` | enum | 是 | `zh` \| `en` | `zh` |
| `model` | string | 是 | 生成该笔记的模型标识 | `deepseek-chat` |
| `prompt_version` | string | 是 | 生成该笔记的提示词版本 | `analyze.v2` |

**同一批笔记的关联方式：** 一次输入拆出的所有笔记共享同一个 `input_id`、`source_hash` 与 `source_ref`。想知道「第一次输入都记了些什么」，按这几个字段筛即可（`list --source`）。**不要把「第一次输入」写进 `tags`**——`tags` 只装知识维度的词（`示例标签`、`子主题`、`工具`），装批次信息会让标签体系很快变脏。

**为什么 `input_id` 要写进每条笔记（而不是只存在台账里）：** `raw/<input_id>.txt` 与 `draft/<input_id>.json` 都是按它命名的。它是笔记文件回到自己原文和草稿的**唯一线索**。如果它只存在台账里，那么台账一丢，`reprocess` 就再也找不到那条笔记的草稿了——而台账是派生数据，本来就允许被删。加了这一个字段，`notes/` 就自成闭环：只给一个 `notes/` 目录，也能重建台账、也能重渲染（见 `decisions.md` D20）。

**为什么 `source_ref` 只存文件名：** 完整路径会泄露用户名、目录结构等私人信息，一旦笔记被分享或同步就跟着出去了。

### 3.2 `status` 语义

| 值 | 写入时机 |
|---|---|
| `inbox` | 用户用 `--yes` 跳过了预览确认（尚未过目） |
| `processed` | 用户在预览后确认（v0.1 的默认路径） |
| `reviewed` | **v0.1 不写入该值**，为将来的复习闭环预留 |

> `status` 在 v0.1 里几乎不起作用，成本≈0。但只写不读的知识库会变成坟墓，这个字段是将来唯一的补救接口——**现在留字段，比将来迁移 500 条笔记便宜得多。**

### 3.3 正文 = 受控块列表

正文由 **`blocks` 数组**渲染而成。**固定的是积木的种类，不是积木的摆法**——每条笔记可以长得不一样，但只能由下面 6 种块拼出来，模型无权发明新类型。

| 块类型 | 结构 | 渲染成 | 典型用途 |
|---|---|---|---|
| `text` | `{ text }` | 普通段落（无标题） | 概述、前置条件、背景 |
| `steps` | `{ title?, items[] }` | `## {title}` + 有序列表 `1.` | 操作步骤 |
| `list` | `{ title?, items[] }` | `## {title}` + 无序列表 `-` | 注意事项、要点清单 |
| `params` | `{ title?, items[{name, value?, note?}] }` | `## {title}` + 表格 | 参数速查 |
| `concept` | `{ term, explanation }` | `### {term}` + 段落 | 术语解释 |
| `uncertain` | `{ items[{text, reason, resolution?}] }` | 文末 `## 待确认` | 拿不准的内容（至多 1 个） |

**渲染规则：**

1. `title` 省略时使用默认标题：`steps` → `操作步骤`，`list` → `要点`，`params` → `参数`。**按 `language` 分两套**：`en` 用 `Steps` / `Key Points` / `Parameters`，`uncertain` 的固定标题是 `Open Questions`（见 decisions.md D17）。标题省略、为空串、或只有空白，一律算「省略」。
2. `concept` 块**不产生 `##` 标题**，直接输出 `### {term}` + 解释段落——概念是笔记里的旁注，不是章节。
3. `uncertain` 块**无论出现在 `blocks` 的哪个位置，一律渲染到文末**，标题固定为 `## 待确认`。**若模型给出了多个 `uncertain` 块，条目合并进同一个标题，一条都不丢。**
4. 文件以 `---` 包围的 YAML frontmatter 开头，与正文之间空一行。
5. 正文首行为 `# {title}`，与 frontmatter 的 `title` **逐字符一致**。
6. 换行统一 `LF`；文件末尾恰好一个换行符。
7. **渲染是确定性纯函数**：同一份 `(NoteDraft, NoteMeta)` 输入，两次运行必须产出逐字节相同的输出。不读时钟、不读文件、不读随机数——`created`/`updated` 由调用方作为参数传入。
8. **frontmatter 的字符串值按需加双引号。** 值以 `- ? : , [ ] { } # & * ! | > ' " % @ \`` 开头、含 `: ` 或 ` #`、以 `:` 结尾、形如数字或 `true`/`false`/`null`/`yes`/`no`、或首尾带空白时，必须用双引号包起来（见 decisions.md D18）。
   > 不加引号的话，一个包含 `: ` 的标题就能把整段 frontmatter 毁掉——**而且毁得非常安静**：文件看着还在，Obsidian 只是不再认得那些字段了。
9. **渲染器拒绝渲染「写出去必然是坏文件」的输入**：任何应当单行的字符串里含换行符，或 `source_ref` 里含路径分隔符，一律当场报错而不是降级输出（见 decisions.md D19）。
   > 正常流程里这些本该由校验环节（第 4.4 节）拦住。渲染器再拦一道，是因为这里放过去的结果不是「难看」，而是「看起来完全正常、其实已经烂了」——正是阶段 1 认定的头号风险。
10. 各块内部：`steps`/`list` 的列表项之间是**单个换行**（用空行隔开会被 Markdown 当成松散列表，每项裹上段落间距）；`params` 的标题与表头之间**空一行**（否则多数解析器不认它是表格）；表格单元格里的 `|` 转义成 `\|`。

**`## 待确认` 的渲染格式：**

```markdown
## 待确认

- 导出清晰：尺寸选择 4K，等比例放大
  - 存疑原因：4K 指工程尺寸还是导出尺寸，原文没有说明
```

用户选择「改写」时，追加一行 `- 更正为：{用户输入}`。

## 4. LLM 输出契约

**LLM 只能产出下面这个结构，不得产出 Markdown。** Markdown 一律由 `render` 从草稿生成。

### 4.1 顶层结构：一次输入 → 多条笔记

```
AnalyzeResult {
  notes: NoteDraft[]        // 0–15 条
}
```

**允许 0 条，但 0 条是一个很窄的口子。** 它只用于「原文里确实没有任何可复用的知识内容」这一种情形（例如原文只有一句「今天没学什么」）。它**不是**模型的退路：

- 原文难懂、看不清、自相矛盾 → 那是 `uncertain` 块的事，**不是** 0 条的理由。
- 原文再短、再乱，只要包含一个可复用的操作、事实或概念，就必须产出笔记。
- 0 条的后果是**这一轮什么都不写**（`notes/` 无新增，台账无新增），所以它必须和「跳过」一样，在终端上明确说出来，不能静默通过。

这条口子存在的理由是：如果没有它，模型面对没有内容的原文时**唯一的出口就是编**——而「不许编」是本项目最重要的内容规则。

### 4.2 NoteDraft

| 字段 | 类型 | 约束 | 允许为空 |
|---|---|---|---|
| `title` | string | 1–80 字符，单行 | 否 |
| `summary` | string | 1–300 字符，单行 | 否 |
| `language` | enum `zh`/`en` | 与原文主要语言一致 | 否（缺省 `zh`） |
| `tags` | string[] | 1–5 项，每项 1–20 字符 | 否 |
| `blocks` | Block[] | 1–12 个 | 否 |

### 4.3 各块字段约束

| 块 | 字段 | 约束 |
|---|---|---|
| `text` | `text` | 1–500 字符 |
| `steps` | `title` / `items` | title 0–40；items 1–15 项，每项 1–300 字符 |
| `list` | `title` / `items` | title 0–40；items 1–10 项，每项 1–200 字符 |
| `params` | `title` / `items` | title 0–40；items 1–15 项；`name` 1–40，`value` 0–40，`note` 0–200 |
| `concept` | `term` / `explanation` | term 1–40，explanation 1–300 |
| `uncertain` | `items` | 1–10 项；`text` 1–300，`reason` 1–200；**整个笔记至多 1 个 `uncertain` 块** |

### 4.4 所有字符串值的通用规则

- **单行纯文本，禁止出现换行符。**
- **禁止以 Markdown 结构符号开头**：`#`、`-`、`*`、`>`、`1.` 等。防止模型在正文里伪造出结构标题。
- 允许行内强调（`**粗体**`、`` `代码` ``）。
- 禁止 Markdown 表格与代码块围栏（``` ```）。
- 校验失败即视为「输出不合契约」，触发重试；重试耗尽后退出码 3。

### 4.5 拆分准则（一次输入拆成几条笔记）

> **一条笔记 = 一件你以后会单独想起来查的事。**

1. **不是按段落拆，不是按课时拆，是按「可独立复用的知识点」拆。**
   通用操作（导入素材、建立工程）与具体效果（加效果）**必须分开**——前者每节课都要用，后者只在做这个效果时用。
2. 每条笔记的标题**不看上下文也必须能看懂**。`加效果` 不合格，`素材加边缘光（提取 + 乙插件）` 合格。
3. 内容本来就单一时，**允许只产出 1 条**。禁止为了凑数硬拆。
4. 禁止把两个互不相关的主题塞进同一条。
5. 原文里的**一句话通常不构成一条笔记**——除非它本身就是一个完整、独立的知识点（例如一句术语定义）。
6. 拆出的笔记**按原文出现顺序**排列。
7. 宁可少拆一条，也不要拆出一条标题不知所云的笔记。

### 4.6 内容准则（此处作为验收依据，同时写进提示词）

1. **不新增**原文没有的事实、数值、参数、按键。
2. **不丢弃**原文的关键结论。宁可原样搬进 `steps`，也不要「概括」掉一个操作。
3. **技术细节逐字保留**：菜单路径（`窗口 → 扩展 → 甲插件`）、参数名（`wave weight`）、按键（`Ctrl+D`、`按住 Alt`）、插件名（`乙插件`、`丙插件`）**必须与原文完全一致**，不许翻译、不许改写、不许"顺手纠正"。
   > 这条是本项目最重要的内容规则。`按住 Ctrl 微调` 被改写成 `按住 Alt` 就是一个**看起来完全正常、但会让你做错操作**的错误——比明显的胡说更有害。
4. **拿不准的不要猜**：真的无法从原文确定的，写进 `uncertain` 块，由用户在预览时裁定（见第 6.3 节）。**不许把猜测当事实写进 `steps` 或 `list`。**
5. `tags` **优先复用**提示词中注入的「已有标签词表」；只有确实没有对应项时才新建标签。

### 4.7 提示词文件契约

提示词是**一等公民**，不是硬编码在 `.ts` 里的字符串——它会被反复迭代，而每次迭代改变的是「用户感受到的质量」。

| 项 | 规定 |
|---|---|
| 位置 | `prompts/<promptVersion>.md`（默认 `prompts/analyze.v2.md`），路径由配置 `promptVersion` 决定 |
| 版本保留 | 发布过的提示词文件**永不删除、永不改写**。笔记 frontmatter 里的 `prompt_version` 是指向它的永久引用——改了它，已经落盘的笔记就再也解释不清自己是怎么来的（D23）。要改提示词，就**新建下一个版本号** |
| 角色 | 它是**系统消息** |
| 用户原文 | 是**用户消息**。**不得**写进提示词文件——文件里只有规则，没有素材 |
| 编码 | UTF-8，全文原样使用，不做任何解析或预处理 |
| 占位符 | **只有** `{{TAG_VOCABULARY}}`，且必须恰好出现一次 |

**占位符规则：**

- 组装时把 `{{TAG_VOCABULARY}}` 替换成「已有标签词表」（一行一个标签，来自 `learnmate tags`）。
- **词表来源 = `notes/` 里所有笔记 frontmatter 的 `tags` 去重**（trim、丢空字符串）。**不是台账**：台账是派生数据、可以整个删掉（§9），而词表不该跟着消失；`docs/02-architecture.md` 第 133 行早就写明这条信息本来就在每条笔记里（D36）。
- 「一行一个标签」这个格式由 `learnmate tags` 命令输出；`add` 与它**共用同一个取词函数**（`src/io/notes.ts` 的 `collectKnownTags`），**不解析命令输出**——否则用户看到的和模型看到的会变成两份可能不一致的东西。
- 一条标签都没有时，替换成一行说明（例如「（还没有任何标签。这是第一批笔记。）」）——**不留下裸露的占位符**。
- 替换是**纯字符串替换**，不引入模板引擎。
- 文件中出现 `TAG_VOCABULARY` 以外的 `{{...}}`、或任何不配对的 `{{` / `}}`，一律**报错拒绝**，不得原样发给模型——否则一个笔误会静默地变成提示词的一部分，而模型只会照做，不会报错。

**版本化规则：**

- 改提示词 = **新建文件**（`analyze.v2.md`）+ 改配置里的 `promptVersion`。**不修改已被使用过的旧文件。**
- `promptVersion` 会写进每条笔记的 frontmatter（见 3.1），所以「这条笔记是哪个版本的提示词产出的」永远可以查——这是提示词迭代唯一的对照依据。
- 提示词文件**进 Git**（它是源码，不是数据）。

## 5. id / slug / 哈希规则

### 5.1 两类 id

| 名称 | 含义 | 生成时机 | 用途 |
|---|---|---|---|
| **`input_id`** | 标识「一次输入」 | `ingest` 阶段 | 命名 `raw/` 与 `draft/` 文件 |
| **`id`** | 标识「一条笔记」 | 拆分之后、每条笔记各一个 | 命名笔记文件、写进 frontmatter |

两者都是 ULID，都一经生成永不变更。**一次输入有 1 个 `input_id`，以及 N 个笔记 `id`。**

### 5.2 ULID

- 26 字符，Crockford Base32（大写；字母表去掉 `I` `L` `O` `U`）。
- **按时间单调递增**，同一毫秒内递增随机部分。

### 5.3 文件名

格式：`<slug>-<id8>.md`，其中 `id8` = **笔记 id** 前 8 字符转小写。

`slug` 生成规则，按顺序执行：

1. 取 `title`，去掉首尾空白。
2. 删除字符：`: * ? " < > | / \` 以及所有控制字符（U+0000–U+001F）。
3. 空白与下划线 → 单个 `-`。
4. 连续 `-` 折叠为一个。
5. 去掉首尾 `-`（**第 7 步截断之后要再执行一次**，见 decisions.md D16）。
6. 若结果忽略大小写后属于 Windows 保留名（`CON` `PRN` `AUX` `NUL` `COM1`–`COM9` `LPT1`–`LPT9`），前置 `n-`。
7. 截断到 60 字符（按 Unicode 码点截断，不切开代理对）。
8. 若结果为空，使用 `note`。
9. **中文、日文等非 ASCII 字符保留原样**（不转拼音、不转码）。

> `id8` 后缀的用意是让「标题相同但内容不同」的两条笔记不会互相覆盖。
> **但它只做到了大部分**：ULID 的前 10 个字符是同一毫秒内共享的时间戳，
> 而同一次输入产出的多条笔记必然在同一毫秒内生成——也就是说它们的 `id8` 完全相同。
> 所以**同一次输入里若出现两条标题相同的笔记，后一条会覆盖前一条**，而且是静默的。
> 这个缺口不能指望文件名规则，必须由 `pipeline` 在写入前统一检查全部目标文件名挡住
> （见 decisions.md 的 TD8 / D29）。**T10 已实现**：`assertSafeTargets` 先算出这一批
> 全部目标文件名，发现批内撞名、或者磁盘上已经有同名文件，就整批不写、退出码 3。
>
> 比较文件名时**忽略大小写**：Windows 与 macOS 的默认文件系统不区分大小写，
> 「Config」与「config」在那里是同一个文件。Unicode 归一化（NFC/NFD）与全角半角
> 折叠还没做，见 decisions.md 的 TD10。
>
> 标题里带 `（` `）` 是安全的——括号不在删除列表里。

### 5.4 指纹

- 算法：**SHA-256**。
- 输入：**规范化文本**按 UTF-8 编码后的字节。
- 表示：`sha256:` + 64 位小写十六进制。
- 一次输入的**全部**笔记共享同一个指纹。

### 5.5 规范化规则（`ingest`）

按顺序执行：

1. 去除 UTF-8 BOM。
2. `\r\n` 与单独的 `\r` → `\n`。
3. 去除零宽字符（U+200B–U+200D、U+FEFF）。
4. 去除每行行尾空白。
5. 连续 3 个及以上**换行**折叠为 2 个（正文里最多保留一个空行）。
6. 去掉整体首尾空白，末尾补一个 `\n`。
7. 长度守卫：字符数按 **Unicode 码点**计（一个汉字、一个 emoji 都算 1 个），**末尾那个由规范化补上的换行不计入**。超过 `maxInputChars`（默认 20000）**直接报错退出（退出码 2），绝不截断**。

> 第 5、7 条的精确含义见 `docs/decisions.md` 的 D15。

> **关键性质（必须写测试）：** 同一段文字分别以 CRLF 和 LF 保存，规范化后**必须得到相同的指纹**。

### 5.6 输入来源（`add` 接受什么）

`add` 认三种输入。**三种最终都变成同一段规范化文本**（5.5），之后走的路完全一样：`ingest` 及其后面的每一步都只看见文本，不知道它原本是什么格式。

| 怎么给 | 读法 | `source_ref` |
|---|---|---|
| `learnmate add 笔记.txt` | 整个文件按 **UTF-8** 解码 | 文件名（含扩展名，不含目录） |
| `learnmate add 笔记.docx` | 先抽取成纯文本（见下） | 同上 |
| 管道；或 `learnmate add -` | 整个标准输入按 UTF-8 读 | **不写**：字段整条不出现 |

- **只看扩展名**（忽略大小写），不看文件内容：命中 `.docx` 才走抽取那条路。其余一切（`.md`、`.txt`、`.doc`、没有扩展名……）都当 UTF-8 文本读。`.doc` 不是压缩包，当文本读只会得到乱码——但扩展名是用户自己给的，工具不替他猜。
- **编码不猜**：只认 UTF-8。GBK 之类的文本会读成乱码，而乱码会照常被送进模型——这是已知的、有意接受的行为（见 D42）。
- **抽取发生在任何写入之前。** 抽取失败（文件损坏、根本不是 Word 文档、通篇图片没有文字）一律退出码 2，此时连 `raw/` 都还没写——「退出码 1 与 2 零写入」的承诺不被这条新路径破坏。
- **`raw/<input_id>.txt` 存的是抽出来的文本，不是原始字节。** 原始 `.docx` 不进知识库、不复制、不留底。代价是：**抽取规则将来变了，没法从 `raw/` 用新规则重抽**——要换抽取器，就得把源文件重新 `add` 一次。（与 D34「已发布的提示词文件永不改写」是同一笔账：知识库只保证解释得了自己是怎么来的，不保证能把自己重新生成一遍。）
- **抽取是有损的，已知丢什么**：页眉、页脚、批注、脚注里的文字；域代码与修订删除的文字（`<w:delText>`）；图片、图表、公式（OMML）的内容。表格拍平成「一行的单元格用 Tab 分隔」。这些内容既不在笔记里，也不在 `raw/` 里。
- 抽出来的文本仍要过 5.5 的规范化与长度守卫：**长度按抽出来的文本算，不按 `.docx` 文件大小算**。
- 实现见 `src/io/readers/docx.ts`，**零新增依赖**（ZIP 的中央目录自己解析，解压用 Node 自带的 `node:zlib`）。理由与天花板见 D42。

## 6. 写入顺序、交互与崩溃语义

### 6.1 写入顺序

写入严格按以下顺序发生，**顺序本身是契约的一部分**：

| 序 | 路径 | 内容 | 时机 |
|---|---|---|---|
| 1 | `.learnmate/raw/<input_id>.txt` | 规范化文本 | **分析之前**，唯一不可跳过、不可撤销的写操作 |
| 2 | `.learnmate/draft/<input_id>.json` | `AnalyzeResult`（全部 N 条草稿） | 模型返回并通过契约校验之后 |
| 3 | `notes/<slug>-<id8>.md` | 渲染产物（**每条被确认的笔记写一个文件**） | 仅在用户确认之后 |
| 4 | `.learnmate/ledger.jsonl` | 审计条目（每条笔记一行，见第 9 节） | 最后，追加写 |

`--dry-run` 是**唯一的例外**：它全程零写入，**连第 1 步的 `raw/` 都不写**（但仍会照常读取输入与调用模型）。见 decisions.md 的 D27。

### 6.2 交互流程（预览 → 逐条确认）

```
$ learnmate add 示例输入.txt

已读取 1378 字，指纹 sha256:3f2a1c9b…
正在分析…（deepseek-chat，8.4s）

拆分为 12 条笔记：
   1. 软件基础设置
   2. 环境与偏好设置
   ...
  12. 示例笔记：先做 A 再做 B

[1/12] 软件基础设置                           tags: 示例 · 软件设置
────────────────────────────────────────────────────────
# 软件基础设置
…
────────────────────────────────────────────────────────
写入这条？ [y] 写入  [n] 跳过  [a] 全部接受  [q] 退出 
```

**存疑项先于写入决定提问**，逐条列出：

```
存疑 1 处：
  [1] 导出清晰：尺寸选择 4K，等比例放大
      我的疑问：4K 指工程尺寸还是导出尺寸，原文没有说明
      [k] 保留为「待确认」  [d] 删除  [e] 我来改写 
```

- `k` 保留（**默认**）：渲染到笔记文末的 `## 待确认`。
- `d` 删除：不写进笔记。
- `e` 改写：用户输入一句话，作为 `- 更正为：…` 写进 `## 待确认`。

**规则：**

- 用户跳过（`n`）一条笔记时：**该条不写入 `notes/`**，其余照常。跳过的笔记留在 `draft/` 里，事后可 `reprocess`。
- `--yes` 跳过所有交互，等价于「全部接受 + 全部存疑项按 `k` 处理」，写入的笔记 `status = inbox`。
- `q` 取消**整批**：这一批一条都不写，**包括之前已经答过 `y` 的那些**（退出码 0）。原文与全部草稿保留，重跑一次就有完整预览。见 decisions.md 的 D28。
- 笔记 id 在**进入预览之前**就全部生成好，预览里显示的 frontmatter 与文件名就是最终要落盘的那些。见 decisions.md 的 D33。
- **无论用户怎么选，`raw/` 与 `draft/` 都保留。** 原文永不丢失。

**产出 0 条时（契约 4.1）：** 不进入预览，直接结束：

```
  这次没有可整理的笔记 —— 原文里没有找到可复用的知识点。
  原文已保存：.learnmate/raw/01J8ZC4M7QX2V9K3TB6NPRW5HE.txt
  没有写入任何笔记。
```

退出码 **0**（什么都没出错）。`notes/` 与 `ledger.jsonl` **都不新增**——没有笔记，就没有可记的行。代价是同一份内容再贴一次会重新分析一次；这个代价可以接受，因为产出 0 条的原文本来就不值得缓存。

### 6.3 崩溃语义

| 崩溃位置 | 残留状态 | 恢复方式 |
|---|---|---|
| 第 1 步之后 | 有原文，无笔记 | 重新 `add` 同一内容：指纹未记账，正常重跑 |
| 第 2 步之后 | 有原文 + 全部草稿 | `reprocess --input <input_id>` 直接重渲染，**不再调用模型**（省钱） |
| 第 3 步写到一半 | 有部分笔记，台账缺条目 | `rebuild-index` 扫描 `notes/` 重建台账 |
| 任意时刻 | —— | **用户原文必定存在** |

> 第 1 步「原文先落盘」是唯一的硬规则：**先保住用户的输入，再去调模型。** 模型超时、返回垃圾、断电，都不能让用户白打一遍字。

### 6.4 原子写入

第 1–3 步的每一次写入都必须原子：**先写同目录下的临时文件，再 rename 覆盖。** 禁止就地追加或截断写——半写的文件比没有文件更糟。

### 6.5 重复输入

`add` 时先查台账：若某个 `source_hash` 已有 `outcome = ok` 的记录，提示

```
这份输入已于 2026-09-28T21:40:11+08:00 处理过，产出 12 条笔记。
如需重新处理，请用 reprocess --input <这次输入的 input_id>，或加 --force 强制重跑。
```

并退出 **0**（不是错误）。`--force` 时正常重跑，新笔记使用新的 id，旧笔记文件保留不动（避免误删）。

## 7. 退出码

| 码 | 含义 | 触发条件 |
|---|---|---|
| 0 | 成功 | 含「已存在，跳过」与「用户取消/跳过」 |
| 1 | 未预期错误 | 未被分类的异常；打印堆栈 |
| 2 | 用法/配置错误 | 参数非法、配置缺失、缺少 API Key、输入超长、源文件读不到或抽不出文字 |
| 3 | 输出校验失败 | 模型输出重试耗尽（现场进 `quarantine/`）；同批笔记的目标文件名撞名（整批不写，草稿已在 `draft/` 里，不另存现场） |
| 4 | 外部服务错误 | 网络失败、超时、限流、鉴权失败 |

规则：**退出码 1 与 2 不产生任何写入**；**退出码 3 与 4 时 `raw/` 必须已存在**。

> 「用户跳过了部分笔记」仍然是成功（0）。只要没有任何一条被写入，也仍然是 0——用户主动不做，不是程序出错。

## 8. 配置契约

`learnmate.config.json`（**不提交**；提交的是模板 `learnmate.config.example.json`）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `vaultPath` | string | `./vault` | 知识库位置，相对**当前工作目录** |
| `model` | string | 无（**必填**） | 模型标识，写入 frontmatter |
| `baseUrl` | string | `https://api.deepseek.com/v1` | 模型服务的 API 根地址，程序会在后面拼 `/chat/completions` |
| `promptVersion` | string | `analyze.v2` | 指向 `prompts/<version>.md` |
| `maxInputChars` | number | `20000` | 输入长度上限 |
| `requestTimeoutMs` | number | `60000` | 单次模型请求超时 |
| `apiKeyEnv` | string | `LEARNMATE_API_KEY` | 存放密钥的**环境变量名** |

> **铁律：API Key 只能来自环境变量，永不写入配置文件。** 配置文件里只允许出现变量名。
>
> `baseUrl` 只支持 `http` / `https`，末尾的 `/` 会被去掉，因为它后面要拼 `/chat/completions`。
> 默认值是 DeepSeek 的 OpenAI 兼容地址；换厂商通常只需要改 `baseUrl` 和 `model` 两个键。

## 9. 台账条目契约

`.learnmate/ledger.jsonl`：每行一个 JSON 对象，**追加写，禁止重写历史**。

台账里的行分**两种**，按 `outcome` 判别。读到一行时先看 `outcome` 是不是 `ok`，就知道该按哪一种形状去读它：

| 种类 | `outcome` | 一行代表 | 什么时候写 |
|---|---|---|---|
| **笔记行** `LedgerNoteRow` | `ok` | 一条笔记 | 产出 N 条笔记 → 写 N 行，每行带同一个 `input_id` |
| **输入行** `LedgerInputRow` | `ok` 以外的任何值 | **一次输入** | 这次输入走到了「原文已落盘」之后，却一条笔记都没产出 |

**笔记行的字段（`outcome = ok`）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | string | ISO 8601 时间戳 |
| `input_id` | string | 本次输入的 id（同批笔记相同） |
| `id` | string | 本条笔记的 id |
| `note_index` / `note_total` | number | 本批中的序号（`3` / `12`） |
| `source_hash` | string | 指纹 |
| `note_path` | string | 笔记路径 |
| `title` | string | 标题 |
| `tags` | string[] | 标签 |
| `status` | string | 写出时的状态 |
| `model` | string | 溯源 |
| `prompt_version` | string | 溯源 |
| `tokens_in` / `tokens_out` | number | 用量（供应商未返回时为 0） |
| `latency_ms` | number | 耗时 |
| `uncertain_total` / `uncertain_kept` | number | 存疑项总数 / 用户选择保留的数量 |
| `outcome` | `'ok'` | 固定值；也是判别两种行的依据 |

**输入行的字段（`outcome ≠ ok`）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | string | ISO 8601 时间戳 |
| `input_id` | string | 本次输入的 id |
| `source_hash` | string | 指纹 |
| `model` | string | 溯源 |
| `prompt_version` | string | 溯源 |
| `outcome` | enum | `skipped` \| `duplicate` \| `cancelled` \| `validation_failed` \| `llm_error` \| `empty` \| `unsafe_write` |
| `reason` | string | 给用户看的一句话（**已压成单行并截断**）——程序**不解析**它，只拿它当说明 |
| `draft_total` | number | 这次输入拆出了几条草稿（模型没答上来时为 `0`） |
| `skipped_total` | number? | 用户按 `n` 跳过几条；**只有 `skipped` 与 `cancelled` 有** |

输入行**没有** `id` / `note_index` / `note_total` / `note_path` / `title` / `tags` / `status` / `tokens_in` / `tokens_out` / `latency_ms` / `uncertain_*`：它不指向任何一条笔记，这些字段没有东西可放。**不许给它们填占位值**——一个永远没人校验的 `note_path` 只会让人以为能顺着它去找文件。

- 台账是**派生数据**：删除整个文件后，`rebuild-index` 必须能从 `notes/` 完整重建。
- 读取时遇到无法解析的行（例如断电导致半行写入）：**跳过并计数，不得崩溃**。
- 读取端的守卫（`isLedgerEntry`）只校验**该分支用途真正依赖的字段**：`ok` 行必须有 `id`（重建要按它去重），两种行都必须有 `input_id` / `source_hash` / `outcome`。多校验一个 `reason` 不会更安全，只会让升级前写下的行集体变成「损坏行」——而损坏行会在下一次 `rebuild-index` 里被静默抹掉。

#### 9.1 「只追加」的唯一天敌：`rebuild-index`

`add` 永远只追加。**唯一**会重写 `ledger.jsonl` 的是 `rebuild-index`——它是修复命令，把 `notes/` 当真相来源重新生成台账。

重建规则：

| 台账里的条目 | 笔记文件 | 重建后 |
|---|---|---|
| `outcome = ok` | 在 | **沿用原条目**（它带着 tokens、耗时、存疑统计），但把 `title` / `tags` / `status` / `note_path` / `source_hash` 刷成笔记文件里的值 |
| `outcome = ok` | 不在 | **剔除**。否则删掉一条笔记之后，同样的内容再也录不进来了 |
| 非 `ok` | 必然没有 | **原样保留**。失败、取消、跳过是纯历史，除了台账没别处记得 |

顺序固定为 `ts` → `input_id` → `note_index`，与文件扫描顺序无关：同一个知识库跑两次必须得到逐字节相同的文件。输入行没有 `note_index`，**按 `0` 参与排序** —— 于是它排在这次输入产出的那些笔记**之前**：先看到「这次输入是什么结局」，再看到它产出的笔记。

#### 9.2 重建 ≠ 还原

**能重建的**：`id`、`input_id`、`ts`（取自笔记的 `created`）、`source_hash`、`note_path`、`title`、`tags`、`status`、`model`、`prompt_version`、`note_index` / `note_total`（按 `source_hash` 分组、按 `id` 排序还原）、`outcome`（一律 `ok`）。

**重建不回来的**：`tokens_in`、`tokens_out`、`latency_ms`、`uncertain_total`、`uncertain_kept` —— **一律补 0**。

补 0 不是「它们是零」，而是「不知道」——笔记文件里从来没有过这些字段，这个信息在写下的那一刻之后就永久消失了。所以：**台账丢了不算灾难，但那些用量数字就是真没了。**（`vault/` 被 gitignore，这些数字也不会出现在 Git 里，想留底得自己把 `ledger.jsonl` 复制一份出去。）

同理，如果某条笔记的 `input_id` 缺失（T7 之前写下的文件），重建会合成一个 `rebuild:<source_hash 前 8 位>` —— 一眼就能看出它**不是**真 ULID，不要拿它去找 `raw/`。

#### 9.3 「原文在，台账就必须有它的行」

**核心不变量：只要 `raw/<input_id>.txt` 存在，`ledger.jsonl` 里就必须有至少一行带这个 `input_id`。**

`raw/` 是「原文已落盘」那一刻写下的，比台账早。所以这条规则的意思是：凡是走到了这一步的输入，台账都得留下它的结局 —— 成功有 N 行 `ok`，其余每一种结局都有对应的那一行输入行。

一次 `add` 的八个出口分别留下什么：

| # | 出口 | 退出码 | 台账 |
|---|---|---|---|
| 1 | 输入超长 | 2 | **不写**（退出码 2 承诺零写入；此时连 `raw/` 都还没有） |
| 2 | 查重命中，直接跳过 | 0 | **不写**（台账是记忆，不是日志；「上次已经录过了」不必每跑一次就记一笔） |
| 3 | 模型输出不合契约，重试耗尽 | 3 | 1 行 `validation_failed`（`draft_total: 0`，现场在 `quarantine/`） |
| 4 | 调用模型失败（网络 / 超时 / HTTP） | 4 | 1 行 `llm_error`（`draft_total: 0`；`reason` **绝不含 API Key**） |
| 5 | 模型说没有可整理的 | 0 | 1 行 `empty`（`draft_total: 0`） |
| 6 | 用户按 `q` 取消整批 | 0 | 1 行 `cancelled`（`draft_total` = 拆出几条；`skipped_total` = 取消前已答 `n` 的条数） |
| 7 | 目标文件名撞名 | 3 | 1 行 `unsafe_write`（`draft_total` = 拆出几条） |
| 8 | 正常写完 | 0 | N 行 `ok`（N = 写出的笔记数）；**用户跳过过笔记再加 1 行 `skipped`**（`draft_total` = 拆出几条，`skipped_total` = 跳过几条）。全部跳过时**只有**这一行 `skipped`，没有 `ok` 行 |

- **出口 5（`empty`）与 `skipped` 是两件事，不许合并成一个值**：`empty` 是「模型的判断」，`skipped` 是「用户的决定」。混在一起，将来按 `outcome` 筛选就分不出来。
- `duplicate` 这个枚举值**保留定义，但没有任何写入路径会产生它**（命中查重时静默返回，见出口 2）。读取端仍必须认得它 —— 历史文件里可能已经有。
- **写台账失败不许掩盖原来的失败**：追加这一行时出错（磁盘满、权限），原来的退出码与错误照原样抛出，只是多打一句警告。台账是记录，不是拦路虎。
- `--dry-run` 凌驾于一切之上：它连这一行也不写，只打印「（--dry-run）本来会……」。体检（`doctor`）、恢复流程（`docs/05-recovery.md`）都以这一节为准。
- **给将来做统计的人**：`tokens_in` / `tokens_out` / `latency_ms` 是**一次调用**的数字，被平铺到同一批的 N 条笔记行上（13 条笔记的这 3 个字段逐字相同）。任何按行求和都是错的，必须先按 `input_id` 去重。输入行根本没有用量字段。本条只是提醒，v0.1 不做任何统计。

## 11. 只读命令契约

> 本节描述 `list` / `show` / `tags` 三个**只读**命令。它们只读 `notes/`，**不读台账**（见 D37），不调用模型，不需要 API Key，也**不写任何文件**——连知识库目录都不会顺手创建。

### 11.1 数据源：笔记文件，不是台账

三个命令的全部输入都是 `notes/` 下 `.md` 文件的 frontmatter（以及 `show` 的正文）。§9 的台账是**派生数据**，按 §9 与 `docs/05-recovery.md` 可以整份删掉再 `rebuild-index`。浏览命令若依赖台账，用户做一次文档明确允许的操作之后就会看到「知识库还是空的」，而磁盘上的笔记一篇没少——**命令输出了与事实相反的话**。所以：

- `list` / `show` / `tags` 一律从 `notes/` 读，台账**删除后行为完全不变**。
- 代价是看不到失败历史（`validation_failed`、`llm_error` 等只记在台账里）。那属于将来的 `history` 命令，不由浏览命令承担。

### 11.2 读不懂的笔记：显示，但不假装读懂了

单篇笔记的 frontmatter 解析失败（§3 的必填字段缺失、`tags` 不是列表等）**不会**让命令报错，也不会让它消失：

- `list` 里照常出现，排最后，行首是 `（读不懂）`，并带上 `problem` 的原因。
- `show` 匹配到它时照常输出正文；默认模式下因为拿不到 frontmatter 的结束位置，**会打出整篇**并向 stderr 说明一句。
- `tags` 跳过它（词表只从读得懂的笔记里取，见 D36）。

理由：坏文件是**用户需要知道的事**，静默吞掉等于让命令撒谎。坏在哪、怎么修，由 `doctor` 负责报告。

### 11.3 `list`

```
<26 位完整 id>  <status>  <created 前 16 字符，T 换成空格>  <标题>  [<标签>/<标签>]
```

真实形状：

```
01M3NRXYPSEJ8PY09XTSZ5S4YA  processed  2026-09-29 13:06  示例笔记：先做 A 再做 B  [示例标签/子主题/工具]
（读不懂）  某个坏文件-01m3nrzz.md  ——  frontmatter 第 3 行不是 `键: 值`
```

- 字段之间是**两个空格**；**不用 `padEnd` 对齐**——中文标题是双宽字符，按字符数补齐必然歪。
- 标签在方括号内按 **UTF-16 升序**排列，与 `renderTagVocabulary`（§4.7）同一个顺序，用 `/` 连接。
- 行首是**完整 26 位 ULID**，刻意**不显示 `id8`**：见 11.5。
- 排序：`created` 字符串比较、新的在前 → `id` 升序 → 读不懂的永远最后、彼此按文件名升序。**两次运行输出逐字节相同**。
- 末尾一行统计：`共 N 篇。`；有读不懂的时 `共 N 篇；其中 M 篇读不懂（frontmatter 坏了，文件还在，用 \`type\` 直接看）。`

选项（可叠加，为「且」）：

| 选项 | 行为 |
|---|---|
| `--tag <标签>` | 只列带这个标签的笔记。**大小写不敏感**（`Demo` 与 `demo` 结果相同）。中文标签不做 ASCII 折叠。 |
| `--status <状态>` | 只列该状态：`inbox` / `processed` / `reviewed`。给别的值**报用法错误、退出码 2**，不许静默当成「0 条」。 |

- 过滤后 0 条**不是错误**：打印一行 `没有符合这个条件的笔记（库里有 N 篇）。`，退出码 0。
- 空知识库（`notes/` 不存在或没有 `.md`）打印两行引导，退出码 0：
  `知识库还是空的（还没有录入过任何笔记）。` / `先跑 node dist/main.js doctor 看看配置，再用 add 录入第一份材料。`

退出码：成功（含过滤后 0 条、含空库）为 0；`--status` 值非法为 2（§7）。

### 11.4 `show <关键词>`

匹配顺序：

1. 关键词是**恰好 26 个字符、且符合 ULID 字符集**时，只按 `frontmatter.id` **精确匹配**（大小写不敏感）。此时**不退回子串搜索**——给出完整 id 的人意图很明确，再去做模糊匹配只会让人困惑。
2. 否则当**子串**，大小写不敏感，同时匹配两处：**文件名（去掉 `.md`）**与 **`frontmatter.title`**。
3. **完全相等优先于子串**。所以 `show 示例` 会命中所有标题含 `示例` 的笔记（本机真实库里是 13 篇），而 `show 示例笔记-先做-A-再做-B-01m3nrxy` —— 它等于某篇笔记的文件名 —— 只命中 1 篇。

结果：

| 命中 | 行为 | 退出码 |
|---|---|---|
| 恰好 1 篇 | 打到 stdout | 0 |
| 0 篇 | stderr 说「没有匹配的笔记」并指向 `list`；stdout 为空 | 2 |
| 多篇 | stderr 打印候选清单；**stdout 为空** | 2 |

- **绝不猜。** 命中多篇时不会「取第一个」「取最新的」或「取最像的」。猜错的代价不是多打一行字，而是用户以为自己在看 A、实际是 B，而且无从上察觉。
- 候选清单最多列 **10** 条，与 `list` **同一个行格式**（含完整 26 位 id），开头一句说清命中了几篇；超出部分折成一行 `…… 还有 N 条，把关键词写长一点再试。` 0 篇与多篇都返回 2，因为用户要做的动作是同一件事：去看 `list`，或者把关键词写具体。

输出分两路（这是一条承诺，不是实现细节）：

- **正文只走 stdout。** `show 示例 > 笔记.md` 存下来的必须就是那条笔记，一个多余字符都没有。
- **提示语、候选清单、警告只走 stderr。**

`--raw` 连 frontmatter 一起打（从第一个字节开始），默认只打 frontmatter 之后的正文，逐字节原样、不格式化、不高亮、不重新排版。frontmatter 读不懂时按 §11.2 处理：默认模式**照样打全文**，并往 stderr 说明一句。

### 11.5 `id8` 不是唯一句柄

从 T12 起，**`id8` 不再被当作识别一篇笔记的方式**：

- `list` 不显示 `id8`。这是有意的：文件名是 `<slug>-<id8>.md`，而 `list` 本来就显示标题，文件名里多出来的信息只有那个 `id8`——而它在本机真实数据里**已经撞了**（13 篇共用一个 `id8`）。显示它等于递给用户一个会误伤的把手。
- 唯一可靠的短句柄是**完整的 26 位 ULID**。
- 想按名字找仍然可以：`show` 的匹配规则包含文件名（去掉 `.md`）与标题。
- 将来若要让 `id8` 变回唯一，那是**改文件名格式**的事，属于另一块工作（当前明确不做）。

### 11.6 `tags`

```
示例标签
子主题
工具
```

- **一行一个标签**，没有前缀、没有 `#`、没有计数、没有颜色。它的输出要能被 `> 词表.txt` 存下来直接当词表用。
- **顺序与提示词里的词表完全一致**（§4.7）：去重、`trim`、丢掉空标签，然后按 **UTF-16 码元升序**。这是 `normalizeTags` 的语义，不按拼音、不按笔画、不按使用次数。
- `--counts` 在每个标签后面追加一个制表符和它被**几篇笔记**用过：`示例标签\t2`。**不改变行的顺序**。一篇里同一个标签写了两遍只算一次——用户想看的是覆盖了多少篇，不是这个词出现过几次。
- 一个标签都没有时打一行 `（还没有任何标签。）`，退出码 0。这与提示词里的 `EMPTY_VOCABULARY`（「还没有任何标签。这是第一批笔记，你可以自由新建。」）**不是同一句话**：命令是给人看的清单，那句话是给模型看的许可。
- **与 `add` 注入的 `{{TAG_VOCABULARY}}` 同源（D36）**：两边都调用 `src/io/notes.ts` 的 `collectKnownTags` 与 `src/core/prompt.ts` 的 `normalizeTags`。不许自己遍历一遍 `notes/`，也不许解析别的命令的输出——两份清单分头演化时，没有任何东西会告诉用户它们不一致。
- 只读、零写入、不调用模型、不需要 API Key。退出码：正常 0；配置读不了按通用错误处理（见 §10 与 `doctor`）。

## 12. 重处理（`reprocess`）

`reprocess` 回答一个问题：**「这份输入当年留下过分析结果，现在我想重新把它写进 `notes/`，但不想再花一次模型调用。」** 因此它和 `add` 的最大区别不是「更高级」，而是**默认一个字节都不联网**。

### 12.1 对象与语法

```
learnmate reprocess --input <input_id>    # 重渲染这一次输入拆出来的全部笔记
learnmate reprocess --note <26 位笔记 id> # 只重渲染这一篇
learnmate reprocess --source <source_hash># 按指纹反查 input_id，再走 --input 那条路
learnmate reprocess --input <input_id> --reanalyze   # 重新分析（会调模型）
```

公共选项：`--dry-run`（走完全部逻辑，一个字节都不写）、`--yes`（跳过逐条确认＝全部接受）。

`--input` / `--note` / `--source` **三选一，恰好给一个**：

- 一个都不给：打印候选清单（每行一个 `input_id`，附**草稿条数**、**盘上已有几篇**、台账行数、有没有裁定文件）并以**退出码 2** 结束，**什么都不处理**。两个条数必须分开报：`01M3PD5P2YBCCR5MYYVX5MWMFQ` 是「草稿 8 条、盘上 0 篇」（当年按 `q` 取消），把它说成「草稿 0 条」会让用户以为没东西可重渲染——而那恰恰是 `reprocess` 最有用的一种输入。草稿读不出条数时报「草稿读不出来」，不假装 0 条，也不让整条命令失败。
- 给两个或更多：退出码 2，零写入。
- 用显式选项名而不是位置参数，是因为 `input_id` 与笔记 id **都是 26 位大写 ULID**，形状完全一样，位置参数会把「选错对象」变成一个安静的灾难。

`--source <source_hash>` 的规则：查台账，**命中一个**就照做；**命中多个就打印候选清单并以退出码 2 结束**，绝不猜（同一个文件被整理过多次时指纹是一样的，本机真实数据里 `sha256:5c095fff…` 就同时对应 3 个 `input_id`）。理由与 `show` 命中多篇时同源（§11.4）。

`--reanalyze` 不能与 `--note` 组合：重新分析的对象永远是**整次输入**，只重做其中一篇在语义上不成立。同时给出时报退出码 2。

### 12.2 默认路径的数据来源

| 数据 | 来源 | 缺失时 |
|---|---|---|
| 分析结果 | `vault/.learnmate/draft/<input_id>.json`（**必需**） | 退出码 2，消息说明「这次输入没有留下草稿，只能 `--reanalyze`」 |
| 存疑项裁定 | `vault/.learnmate/resolutions/<input_id>.json`（可选） | 视为「用户没改过任何存疑项」，照原草稿渲染 |
| 元数据 | 见下表 | 见下表 |
| 原文 `raw/<input_id>.txt` | **不读**（不调模型就不需要原文） | 不影响 |

**元数据来源优先级**：

| 字段 | 第一来源 | 第二来源 | 都没有 |
|---|---|---|---|
| `source_hash` | 台账里该 `input_id` 的任意一行 | 既有笔记 frontmatter | 从 `raw/<input_id>.txt` 重算（`src/util/hash.ts`；原文规范化是幂等的，重算与当年一致） |
| `model` / `prompt_version` | 台账 | 既有笔记 frontmatter | 退出码 3，提示「只能用 `--reanalyze` 重新分析」 |
| `id` | 既有笔记 frontmatter（按标题配对） | 新造 ULID | — |
| `created` | 既有笔记 frontmatter（**保持不变**） | 当前时间 | — |
| `updated` | 内容真变了才写当前时间 | 内容没变就**不动** | — |
| `status` | 既有笔记 frontmatter（保持不变） | `--yes` 时 `inbox`，否则 `processed` | — |
| `source_ref` | 既有笔记 frontmatter | 不写 | — |

**为什么靠标题配对、不靠台账的 `note_index`**：用户当年在预览里按 `n` 跳过某几条时，台账只记了 `skipped_total` 这个**计数**，没记跳过的是哪几条；而 `rebuild-index` 重建出来的 `note_index` 是按 `id` 排序重新推的，跳过的空档会被抹平。台账的 `note_index` 只当**一致性校验**：能对上就信，对不上就以标题为准并打一行警告。标题可以当配对依据，是因为 `src/core/validate.ts` 强制**同一次输入内标题不重复**（`LIMITS` 之外唯一一条会改模型输出的约束）。

**配对范围限定在「这次输入自己产出的笔记」**：愿意当配对目标的，`frontmatter.input_id` 必须**等于**正在重处理的 `input_id`。这一步不是可选的优化，是防串代：

> 同一份原文被整理过两次是完全正常的（真实数据里 `01M3NR4AMKFP6HMM31WYSTTSSX` 与 `01M3PD5P2YBCCR5MYYVX5MWMFQ` 就是同一份原文的两代产出，各拆出 13 篇与 8 篇，标题大量重叠）。
> 不限定 `input_id` 的话，重处理第二代会把第一代的笔记按标题「配上对」然后就地覆盖——那些笔记的 `id` 与 `created` 是第一代的，内容被换成第二代的，`input_id` 还会被改写成第二代，等于把两代搅在一起，而用户根本没要求动第一代。
> 配不上就按「盘上没有」处理：新造 `id`、当新笔记写出来。所以上面例一那种「当年被 `q` 取消、盘上一篇都没有」的输入，8 条草稿就该是 **8 篇新笔记**（不是 3 篇覆盖 + 5 篇新建）。

同理，`orphanExisting`（「盘上有、草稿里没有」的计数）也只统计这次输入自己的笔记，否则会把知识库里无关的笔记一并报成「在这次草稿里找不到对应」。

配对的结果：

- 草稿里有、盘上没有 → 新造 `id`，当**新笔记**写出来。
- 盘上有、草稿里没有 → **不动它**，末尾列出「这 N 篇笔记在这次草稿里找不到对应，已跳过」。
- 草稿被手工改出两条同标题 → 退出码 3，零写入（没法判断各自对应哪一篇）。

### 12.3 幂等与副作用

- **内容没变就一个字节都不写**：`renderNote` 的结果与盘上那篇**逐字节比较**，一样就跳过写入，连 `updated` 也不动。这是真幂等——连跑两次，第二次零写入。比较**不做换行归一化**：比较用的字节必须就是盘上那串字节。
- 内容不一样才原子覆盖；写入时 `updated` 刷成现在，`created` 保持原值。
- 文件名默认不变（标题来自同一份草稿）。例外：手工改过草稿标题、或 `slugify` 规则变了，会算出另一个文件名——那时旧的留在原地、新的是一个新文件（配对靠标题，对不上就是新的一条）。
- **覆盖白名单**：`assertSafeTargets` 泛化出一个「允许覆盖」参数，白名单里只放**本次要改写的那几篇自己的目标路径**。白名单之外的文件照样存在就整批拒绝（D29 精神不变）。新建笔记**永远不进白名单**：它的文件名是新算出来的，落在已存在的文件上就说明算错了，必须整批拒绝而不是顺手盖掉别人的笔记。
- 覆盖真实笔记前**默认逐条确认**（`add` 那套 `[y]/[n]/[a]/[q]`）。`--yes` 跳过。理由：`vault/` 不在 Git 里（D8），没有版本可回退。
- **默认路径不重新问存疑项**：有裁定文件就重放，没有就一律按 `keep`（渲染成 `## 待确认`）。想重新决定请用 `--reanalyze`。
- **既有笔记的 `status` 原样沿用，绝不重算**。这不是审美问题，是幂等的前提：`--yes` 新建时写进 frontmatter 的是 `inbox`（与 `add --yes` 一致），若重算成固定的 `processed`，第二次重跑就会把每一篇都改一遍并报「N 条会改写」——幂等当场断在 `status` 上。同理，`updated` 只在内容真的要写时才刷新（见上一条）。
- `--dry-run` 走完全部逻辑但不写任何文件，输出「会新建哪几篇 / 会改写哪几篇 / 哪几篇未变化」。
- 逐条写、**没有整体事务**：写到第 3 篇崩了，前 2 篇是新的。不需要额外补救机制——重跑 `reprocess` 即可，幂等保证已写好的会被认成「未变化」。

### 12.4 台账分工

**默认重渲染一行台账都不写。** 三条理由：

1. 台账记的是**每次输入的结局**，重渲染不改变结局。
2. 台账只追加（`appendText`），而重渲染要动的是既有 `ok` 行的派生字段（`title` / `tags` / `status` / `note_path`）——按 §9.1，刷新这些正是 `rebuild-index` 的活。
3. 零契约变更：不用新增 `outcome` 值，不用改两种行形状。

代价：重渲染之后 `ok` 行与 `notes/` 会暂时对不上。对策是命令结束时明确打印：

```
台账没有改动；要看刷新后的索引请运行 learnmate rebuild-index
```

`--reanalyze` **不受此限**：它是一次全新的输入，按 §9.3 的八出口表正常记录。

### 12.5 `--reanalyze` 与 `add --force` 的对照

两者的本质都是「同一份原文再跑一次分析」，差别只在原文从哪来、以及旧笔记怎么办：

| | `add --force` | `reprocess --reanalyze` |
|---|---|---|
| 原文从哪来 | 重新读磁盘上的源文件 + `ingest` 规范化 | 读 `raw/<input_id>.txt`（那份**已经规范化过了**） |
| 查重 | `--force` 绕过 | 显式要求重分析，默认就绕过，不需要再加 `--force` |
| `source_ref` | 有源文件名 | **没有**：`raw/` 只存正文，源文件名只有原笔记的 frontmatter 记得，台账和草稿里都没有 |
| 旧笔记 | 原地不动（§6.5：新笔记用新 `id`、旧文件保留） | 用户确认后搬进 `vault/.learnmate/trash/`（撞名加 `.<n>` 后缀） |
| 需要 API Key | 是 | 是 |
| 是否新造 `input_id` | 是 | 是 |

`source_ref` 那一行是 `--reanalyze` **唯一的信息损失**，用这条路产出的笔记 frontmatter 里不会有 `source_ref`。

顺序是有意的：读原文 → 分析 → 校验通过 → 用户确认 → **搬旧的** → 写新的。这样按 `q` 取消、或全部答 `n` 时，旧笔记原封不动。

- 不新建 `prompts/analyze.v3.md`：`--reanalyze` 用配置里的 `promptVersion`（默认 `analyze.v2`），新笔记 frontmatter 如实记这个值。已发布的提示词文件永不删改（D34）。

### 12.6 明确不做

- 不做 `--all`（批量重处理整个知识库）。
- 不做笔记的删除、合并、拆分（那是 TD7）。`trash/` 只服务于 `--reanalyze` 换掉自己造出来的那一批。
- 不做笔记版本历史（TD1）。`resolutions/` 不承担历史功能。
- 不改提示词、不新建 `analyze.v3.md`。
- 不做 `history` 命令，也不做 `--list` 之外的浏览功能。
- 不做时间戳 hack（不加 `--touch` 之类，`updated` 只在内容真变时刷新）。
- 不改 frontmatter 结构、不改块枚举、不改 `draft/` 既有格式（`schema_version` 保持 1，28 篇旧笔记和全部旧草稿一个都不用迁移）。
- 不自动跑 `rebuild-index`（D22 的分工，`reprocess` 只提示不代劳）。
- 不手工进 `quarantine/` / `trash/` 做垃圾回收。
- 不解决 TD14、TD15。
